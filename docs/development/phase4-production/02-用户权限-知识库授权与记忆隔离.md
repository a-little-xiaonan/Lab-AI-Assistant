# Phase 4 · 02 用户权限、知识库授权与记忆隔离 — 实现技术方案

> **所属阶段**：Phase 4 — 多用户化基础能力
> **前置依赖**：Phase 1～3 已完成的聊天、知识库、会话与记忆能力
> **关联设计**：[用户、知识库与记忆关系设计](../../design/用户-知识库-记忆关系设计.md)
> **状态**：核心功能已实施（2026-09-01）
> **适用场景**：实验室招新助手从本地单用户 RAG 升级为面向新生、成员和管理员的多用户系统。

---

## 1. 目标与边界

本方案一次补齐四项能力：

1. **用户系统**：注册、登录、刷新登录态、登出、账号禁用。
2. **角色权限**：新生、内容管理员、系统管理员的 RBAC 权限控制。
3. **知识库授权**：公开、登录可见、受限知识库及用户/角色级授权。
4. **用户级记忆隔离**：会话和长期记忆都绑定用户，杜绝不同新生之间的记忆串用。

不在本次范围内：第三方登录、短信/邮件验证码、单点登录、Redis 集群、细粒度审批流、完整运营后台。这些可在基础认证稳定后继续扩展。

### 当前实现范围

- 已实现：Argon2 密码哈希、JWT Access Token、Refresh Cookie 轮换、注册/登录/登出、RBAC、知识库 ACL、会话归属校验、用户级长期记忆隔离、短期摘要持久化、个人记忆页、用户角色页和角色授权页。
- 当前保留为下一阶段：Alembic 正式迁移版本库（本次沿用项目既有的启动期增量迁移）、登录/上传限流、审计日志实际写入、敏感信息过滤、匿名会话认领、用户级授权的可视化界面。

## 2. 关键决策

| 决策 | 方案 | 原因 |
| --- | --- | --- |
| 身份认证 | 用户名/密码 + 短期 Access Token + 长期 Refresh Token | 适合现有 Vue + FastAPI 架构，先不依赖第三方平台 |
| 密码存储 | `pwdlib[argon2]` 哈希 | 不保存明文密码；Argon2 适合新系统 |
| Access Token | 15 分钟 JWT，前端仅存内存，通过 `Authorization: Bearer` 发送 | 减少长期 Token 被浏览器脚本窃取的风险 |
| Refresh Token | 7 天，HttpOnly + Secure + SameSite=Lax Cookie，数据库只存 hash | 支持刷新登录态，也可服务端吊销 |
| 角色模型 | RBAC：`student`、`editor`、`admin`；`guest` 为未登录状态而非数据库角色 | 简洁且满足招新场景；避免为每个访客建账号 |
| 知识库授权 | 可见性 + 角色授权 + 用户例外授权 | 能覆盖公开资料、登录资料、成员内部资料与个别例外 |
| 长期记忆 | MySQL 管理副本 + ChromaDB 统一 `user_memories` collection，强制 `user_id` 过滤 | 用户可查看/删除；向量召回不串用；不产生大量小 collection |
| 会话删除 | 保留现有逻辑删除；恢复、查看、删除均需验证会话所有权 | 满足可恢复要求，防止通过猜测 session ID 访问别人历史 |

## 3. 目标架构

```text
Vue 前端
  ├─ 登录态：Access Token（内存）+ Refresh Cookie
  ├─ 招新用户：浏览公开/登录可见知识库、管理自己的会话和记忆
  └─ 管理员：知识库、文档、用户、授权管理

FastAPI
  ├─ auth：认证、令牌刷新、当前用户
  ├─ authorization：角色权限、会话归属、知识库访问控制
  ├─ chat：鉴权后检索、生成、保存用户会话
  ├─ memory：仅查询和写入当前用户的长期记忆
  └─ admin：用户状态、角色、知识库授权

MySQL
  ├─ users / roles / user_roles / refresh_tokens
  ├─ knowledge_bases / knowledge_base_role_permissions / knowledge_base_user_permissions
  ├─ sessions / messages / user_memories
  └─ audit_logs

ChromaDB
  ├─ kb_{kb_id}_docs         公共知识库文档向量
  └─ user_memories           用户长期记忆向量（metadata.user_id 强制过滤）
```

## 4. 数据库设计与迁移

当前项目使用 MySQL，现有 `create_all + ALTER TABLE` 方式可以继续支撑小迁移；本次涉及多张关联表和索引，建议从本条目开始引入 **Alembic** 管理版本化迁移。旧的启动期迁移保留，后续新结构不再继续堆叠手写 `ALTER TABLE`。

### 4.1 用户与认证表

```text
users
- id                    varchar(64), PK，user_ 前缀 UUID
- username              varchar(64), UNIQUE，登录名
- password_hash         varchar(255)
- nickname              varchar(64)
- email                 varchar(255), NULL，UNIQUE
- status                varchar(16)  active / disabled / deleted
- created_at
- updated_at
- last_login_at
- deleted_at

roles
- id                    varchar(64), PK
- code                  varchar(32), UNIQUE：student / editor / admin
- name                  varchar(64)
- description

user_roles
- user_id               FK users.id
- role_id               FK roles.id
- created_at
- UNIQUE(user_id, role_id)

refresh_tokens
- id                    varchar(64), PK
- user_id               FK users.id
- token_hash            varchar(255), UNIQUE
- expires_at
- revoked_at
- created_at
- user_agent            varchar(255), NULL
- ip_address            varchar(64), NULL
```

种子角色：

| code | 用途 |
| --- | --- |
| `student` | 已注册新生；可查询授权知识库、管理自己的会话与记忆 |
| `editor` | 实验室内容维护成员；可维护被授权知识库的文档与索引 |
| `admin` | 管理用户、角色、授权和系统级知识库 |

未登录状态通过 `current_user is None` 表示，不创建 `guest` 数据库行。

### 4.2 知识库授权表

不使用无外键约束的 `subject_type + subject_id` 多态表。为了让 MySQL 保证引用完整性，拆为两张 ACL 表：

```text
knowledge_bases（已有表扩展）
- visibility            public / authenticated / restricted
- owner_id              FK users.id，NULL 表示系统所有
- status                active / archived / deleted
- updated_at

knowledge_base_role_permissions
- kb_id                 FK knowledge_bases.id
- role_id               FK roles.id
- permission            read / write / manage
- created_at
- UNIQUE(kb_id, role_id, permission)

knowledge_base_user_permissions
- kb_id                 FK knowledge_bases.id
- user_id               FK users.id
- permission            read / write / manage
- created_at
- UNIQUE(kb_id, user_id, permission)
```

权限判定规则：

1. `admin` 始终拥有全部权限。
2. `owner_id == current_user.id` 默认拥有 `manage`。
3. `public` 默认授予所有人 `read`。
4. `authenticated` 默认授予已登录用户 `read`。
5. `restricted` 仅授予 ACL 中明确拥有 `read/write/manage` 的用户或角色。
6. `manage` 隐含 `write` 与 `read`；`write` 隐含 `read`。

### 4.3 会话与消息迁移

在现有 `sessions` 表增加：

```text
sessions
+ user_id               FK users.id，NULL 表示匿名会话
+ anonymous_id          varchar(64)，匿名浏览器标识；登录用户为空
+ summary               TEXT，持久化历史摘要
+ name_source           ai / user / system
+ visibility            private（预留；当前不实现共享会话）
```

约束：`user_id` 与 `anonymous_id` 必须至少存在一个；登录后可将匿名会话显式迁移给当前用户。这个“认领会话”操作必须由用户主动确认，不自动合并。

**重要行为变更**：

- 当前“传入不存在 session_id 就自动创建”的行为改为：带 `session_id` 但查不到或不属于当前用户时返回 404；不传 `session_id` 才创建新会话。
- 已逻辑删除会话不再因聊天请求自动复活；只能调用恢复接口，并验证所有权。
- 现有会话没有用户归属。迁移脚本必须显式要求指定初始管理员账号，才可将历史会话归到该账号；未迁移会话统一标记为 `legacy/unclaimed`，默认不对任何新生开放。

### 4.4 用户长期记忆表与向量元数据

新增 MySQL 管理表：

```text
user_memories
- id                    varchar(64), PK，mem_ 前缀 UUID
- user_id               FK users.id，INDEX
- memory_type           profile / preference / fact / goal
- content               TEXT
- content_hash          char(40)，同一用户去重
- confidence            decimal(4,3)
- source_session_id     FK sessions.id，NULL
- scope_kb_id           varchar(64)，NULL，仅作业务语境标记
- status                active / deleted
- expires_at            NULL
- created_at
- updated_at
- UNIQUE(user_id, content_hash)
```

ChromaDB 改为统一集合：`user_memories`。每条向量必须携带：

```json
{
  "memory_id": "mem_...",
  "user_id": "user_...",
  "memory_type": "preference",
  "source_session_id": "sess_...",
  "status": "active"
}
```

查询时固定使用：

```python
where={"user_id": current_user.id, "status": "active"}
```

`user_id` 只能来自后端认证依赖，不能由前端请求体传入后直接使用。

### 4.5 审计日志

```text
audit_logs
- id
- actor_user_id         FK users.id，NULL 允许系统任务
- action                login / role_change / kb_permission_change / document_delete ...
- resource_type
- resource_id
- detail_json           JSON
- created_at
```

记录管理操作和授权变化；不记录密码、Token、完整 Prompt 或敏感个人记忆正文。

## 6. 认证与授权实现

### 6.1 登录流程

```text
POST /api/auth/login
  → 校验 username + password
  → 校验 users.status == active
  → 签发 15 分钟 Access Token（响应 JSON）
  → 生成随机 Refresh Token
  → 仅把 Refresh Token 的 hash 存 MySQL
  → 原始 Refresh Token 写 HttpOnly Cookie
  → 写 audit log
```

刷新流程：

```text
POST /api/auth/refresh
  → 从 HttpOnly Cookie 读取 Refresh Token
  → 计算 hash，检查未吊销且未过期
  → 吊销旧 Refresh Token，签发新 Refresh Token（旋转）
  → 返回新 Access Token
```

登出时撤销当前 Refresh Token，并清除 Cookie。账号禁用后，认证依赖每次都校验 `status=active`，使旧 Access Token 最迟在下一次请求失效。

### 6.2 FastAPI 依赖

```python
get_optional_current_user() -> User | None
get_current_user() -> User
require_role("editor", "admin") -> User
require_session_owner(session_id, current_user) -> ChatSession
require_kb_permission(kb_id, current_user, "read") -> KnowledgeBase
```

接口分层：

- 公共知识库列表与公开聊天：使用 `get_optional_current_user()`。
- 已登录功能：使用 `get_current_user()`。
- 文档上传、删除、重索引：使用 `require_kb_permission(..., "write")`。
- 知识库删除和授权管理：使用 `require_kb_permission(..., "manage")`。
- 系统用户与角色管理：使用 `require_role("admin")`。

### 6.3 聊天检索接入点

聊天接口不能再直接相信请求中的 `knowledge_base_id` 和 `session_id`：

```text
请求进入
→ 获取当前用户或匿名身份
→ 若带 session_id：验证该会话属于当前身份
→ 若不带 session_id：创建归属当前身份的新会话
→ 校验用户对 kb_id 的 read 权限
→ 检索该知识库
→ 仅召回当前用户的长期记忆
→ 写消息、摘要、长期记忆
```

匿名用户只允许：

- `public` 知识库的 `read`。
- 匿名会话的短期上下文。
- 不生成长期记忆、不访问管理接口。

## 7. 长期记忆迁移方案

当前实现把长期记忆放在 `kb_{kb_id}_memory` 中，并在同一知识库内跨会话召回。这对单用户本地模式可用，但多用户上线后有隐私风险。

迁移步骤：

1. 上线新表与 `user_memories` collection，但暂不删除旧 memory collection。
2. 新代码仅写入和读取 `user_memories`，并强制 `user_id` 过滤。
3. 旧 memory collection 因为缺少可靠 `user_id`，默认不再被召回。
4. 如果历史会话能被明确归属到初始管理员，可通过一次人工确认迁移；无法确认归属的旧记忆不迁移。
5. 观察期结束后，再由管理员手动归档或删除旧 `kb_{kb_id}_memory` collection。

这是一项隐私优先的迁移：宁可丢弃无法归属的旧个性化记忆，也不能把它暴露给新用户。

## 8. Prompt 与记忆写入规则

目标 Prompt 顺序：

```text
System Prompt
→ 当前用户长期记忆（top 3）
→ 当前用户有权访问的知识库检索片段
→ 当前会话摘要
→ 最近 N 轮消息
→ 当前问题
```

规则：

- 长期记忆只用于个性化回答，例如推荐学习路径或调整表达方式。
- 实验室客观事实只能由知识库检索片段支撑，并保留来源标注。
- 记忆提取前增加敏感信息过滤：手机号、身份证号、住址、密码、Token 等不入库。
- 记忆提取时写入 `user_id`、`source_session_id` 和内容 hash；同用户相同内容使用 upsert。
- 用户删除一条记忆：MySQL 标为 `deleted`，同时删除 ChromaDB 对应 vector；两边操作必须可重试。
- 会话逻辑删除不自动删除用户长期记忆；长期记忆由用户在“我的记忆”页面单独管理。

## 9. API 设计

### 9.1 认证

```text
POST /api/auth/register
  body: {username, password, nickname, email?}
  → 201 {user}

POST /api/auth/login
  body: {username, password}
  → 200 {access_token, token_type: "bearer", user}

POST /api/auth/refresh
  → 200 {access_token, token_type: "bearer"}

POST /api/auth/logout
  → 204

GET /api/auth/me
  → 200 {id, username, nickname, roles, status}
```

注册策略首期建议开放注册，但加上用户名长度、密码强度、IP 限流；如果后续只面向校内新生，可改为管理员邀请或校园邮箱验证。

### 9.2 用户自身资源

```text
GET    /api/users/me/sessions?include_deleted=false
PUT    /api/users/me/sessions/{id}/restore

GET    /api/users/me/memories
PUT    /api/users/me/memories/{memory_id}
DELETE /api/users/me/memories/{memory_id}
DELETE /api/users/me/memories
```

现有 `/api/chat/sessions/*` 可以保留路径，但内部必须改用当前用户做归属过滤；前端不需要在 URL 中携带 user_id。

### 9.3 知识库与授权

```text
GET    /api/knowledge-bases
  → 仅返回当前用户可见的知识库

POST   /api/knowledge-bases
  → admin 创建；owner_id = 当前用户

POST   /api/knowledge-bases/{kb_id}/role-permissions
DELETE /api/knowledge-bases/{kb_id}/role-permissions/{id}
POST   /api/knowledge-bases/{kb_id}/user-permissions
DELETE /api/knowledge-bases/{kb_id}/user-permissions/{id}
```

### 9.4 管理接口

```text
GET /api/admin/users
PUT /api/admin/users/{user_id}/status
PUT /api/admin/users/{user_id}/roles
GET /api/admin/audit-logs
```

所有写接口继续沿用项目既有错误格式：

```json
{"detail": {"code": "forbidden", "message": "无权访问该知识库"}}
```

## 10. 前端实现

### 10.1 新增页面与状态

```text
frontend/src/
├── api/identity/auth.ts
├── api/identity/users.ts
├── stores/auth.ts
├── views/identity/LoginView.vue
├── views/RegisterView.vue
├── views/identity/ProfileView.vue       # 我的资料与我的记忆
├── views/admin/identity/AdminUsersView.vue
└── components/RouteGuard.vue
```

前端行为：

- `auth` store 只保存 Access Token 与当前用户；刷新页面时调用 `/api/auth/refresh` 恢复登录态。
- 知识库下拉只展示后端返回的可访问知识库。
- 未登录用户可进入公开聊天；进入个人会话、我的记忆、管理页时跳转登录。
- “我的记忆”页面展示内容、类型、来源会话、创建时间，支持删除和清空。
- 管理页仅对 `admin` 显示入口；即使前端入口被绕过，后端也必须返回 403。

### 10.2 会话前端调整

- 所有会话列表由后端按当前用户过滤。
- 已删除会话放入“最近删除”，可在保留期内恢复。
- 旧的“自动复活会话”交互改为明确的“恢复会话”按钮。
- 注册登录后可以选择认领当前匿名会话；不勾选则保持匿名并按过期策略清理。

## 11. 实施顺序

### 11.1 第一步：数据库与迁移基础

3. 扩展 `knowledge_bases` 和 `sessions`。

5. 写入角色种子与初始管理员创建命令。

### 11.2 第二步：认证与会话归属

2. 实现 `/api/auth/*` 与 `get_current_user()`。
3. 给聊天、会话接口接入会话所有权验证。
4. 移除“未知 session_id 自动创建、已删除 session 自动复活”的旧逻辑。

### 11.3 第三步：知识库权限

1. 实现 `require_kb_permission()`。

4. 将现有 `kb_default` 标记为 `public`，并将系统管理员作为 owner。

### 11.4 第四步：用户级长期记忆

1. 新建 `UserLongTermMemory`，替换当前按 kb 共享的 `LongTermMemory`。

4. 将短期摘要写回 `sessions.summary`，重启后直接加载而不是反复调用 LLM 重算。
5. 实现“我的记忆”接口和前端页面。

3. 添加敏感信息过滤规则。
4. 执行旧会话、旧记忆迁移与归档。

## 12. 验收标准

- 访客只能看到和检索 `public` 知识库。
- 登录新生只能读取自己会话、自己的长期记忆和被授权知识库。
- 新生 A 使用 session_id 访问新生 B 的会话，返回 404 或 403，不泄露会话是否存在。
- 即使前端伪造 `user_id`，长期记忆召回仍只返回认证用户自己的内容。
- 内容管理员可以处理被授权知识库文档，但不能默认读取所有新生记忆。
- 管理员撤销用户对受限知识库的权限后，下一次聊天检索立即无法命中该库。
- 用户删除会话后可以恢复；删除长期记忆后不再参与 Prompt。
- 服务重启后，会话摘要仍能从 `sessions.summary` 正确恢复，无需再次调用 LLM 生成旧摘要。
- 旧 `kb_{kb_id}_memory` 数据不会被新多用户链路召回。
- 登录、刷新、登出、账号禁用和 Refresh Token 吊销均可用。

## 13. 风险与注意事项

- **最大风险是权限遗漏**：新增任何知识库相关接口，都必须检查 `read/write/manage`，不能只保护前端路由。
- **ChromaDB 的 where 过滤是安全边界的一部分**：用户记忆查询遗漏 `user_id` 的后果是跨用户隐私泄露，应封装在唯一的 memory store 方法中，禁止业务代码自行 query。
- **不要把 Access Token 长期存在 localStorage**：短期内存 Token + HttpOnly Refresh Cookie 的实现复杂一点，但更适合多用户系统。
- **旧数据不可自动认领**：没有可靠 user_id 的历史会话和记忆必须隔离，不能猜测归属。
- **权限缓存要谨慎**：首期不缓存授权结果；如以后接入 Redis，只缓存短时间的只读权限结果，并在授权变更时主动失效。
- **访客与注册用户分界明确**：访客不建立永久长期记忆，避免未授权个人画像积累。
