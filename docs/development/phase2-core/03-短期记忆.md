## 1. 目标与范围

会话级的对话历史管理：滑动窗口保留最近 N 轮，超出窗口时用 LLM 摘要压缩旧对话；历史拼入 prompt（对齐 §7.4 组装结构）。历史数据源自 SQLite（Phase 1-07 落库），会话重启不丢。

## 2. 任务拆解

- [x] `app/memory/short_term.py`：按 §7.2 伪代码实现
  - `ShortTermMemory(session_id, max_turns=10)`
  - `add_message(role, content)`：追加消息；`len(messages) > max_turns * 2` 时触发 `_compress()`
  - `_compress()`：旧消息（前 `max_turns` 条）→ `llm_summarize` 摘要 → 摘要存 `self.summary`，旧消息移除
  - `get_context()`：`[历史摘要] ...` + 剩余消息（对齐 §7.2 的 context 格式）
- [x] `app/memory/memory_manager.py`：统一入口
  - `get(session_id) -> ShortTermMemory`（进程内 dict 管理实例）
  - `load_from_db(session_id)`：从 SQLite 读历史重建窗口（重启恢复）
  - 每轮对话收尾：`add_message("user", q)` + `add_message("assistant", a)`，并落库
- [x] `rag_pipeline` 接入：`build_prompt` 中历史段来自 `short_term.get_context()`（对齐 §7.4 第 3 步）
- [x] Token 预算（§6.1）：历史段 ≤ 4000 token；超限时优先触发摘要压缩，其次丢弃最旧消息
- [x] 摘要降级：LLM 压缩失败 → 直接丢弃最旧消息（日志记录），不让主链路受影响

## 3. 设计要点

- **压缩触发点**：消息条数 > `max_turns * 2`（§7.2 约定；`max_turns` 从配置读，默认 10）
- **数据源统一**：ShortTermMemory 是**运行时视图**，SQLite 是**持久层**；内存实例只服务当前进程，重启后从库重建（窗口/摘要按重建规则重新计算）
- **摘要也进上下文**：`[历史摘要]` 段 + 窗口内消息拼接，保证被压缩的旧信息仍有一份浓缩备份
- **模型调用**：`llm_summarize` 复用 `qwen.chat_completion`，prompt 要求只输出摘要正文（控制在 300 token 内）
- 与长期记忆（Phase 3-03）分工：短期管「本会话的上下文连续性」，长期管「跨会话的事实沉淀」，两者各自独立实现、拼装顺序不同（§7.4）

## 5. 验收标准

- [x] 连续 20 轮对话：前 10 轮被压缩为摘要（日志可见 `_compress` 触发），后续回答仍能理解早期信息（如"我之前问过的问题"）
- [x] 重启服务后继续同一 session 对话，历史完整（从 DB 重建）
- [x] 历史段拼入 prompt 后总 token 不超预算（超限时正确触发压缩/丢弃）
- [x] mock LLM 摘要失败时：对话不中断，最旧消息被丢弃并记录日志
- [x] 不同 session 的记忆互不串扰（实例按 session_id 隔离）

## 6. 风险与注意事项

- **摘要丢失细节**：压缩后早期细节可能丢失，`max_turns` 可配置权衡；摘要 prompt 要求保留"事实与偏好"类信息（与长期记忆的口径一致）
- **内存泄漏**：进程内 dict 缓存会话实例，需带容量上限与过期清理（如 LRU 或按最后访问时间淘汰），否则长驻服务内存膨胀
- **压缩延迟**：摘要是一次额外 LLM 调用，放在对话收尾的异步路径执行（不阻塞用户下一次提问的响应）；MVP 可接受同步执行，但标注 TODO
