## 1. 目标与范围

固化并优化 prompt 模板体系（分场景模板），规范化引用来源标注格式，并建立 QA 评估样例集，作为后续阶段（Query Rewrite / Re-rank）效果对比的基线。

## 2. 任务拆解

- [x] `app/llm/prompt_templates.py` 模板体系（基于 §4.2 示例模板拆分）：
  - `rag_answer`：标准回答模板（系统提示 + 参考资料 + 对话历史 + 问题）—— 主场景
  - `no_context`：检索为空/全被阈值过滤时使用，明确告知"知识库中未找到相关内容"并可给出建议（换措辞/上传文档）
  - `summarize_history`：短期记忆压缩用（Phase 2-03 引用）
  - `query_rewrite`、`memory_extract`：Phase 3 预留占位（模板先定义，实现后置）
- [x] 引用标注规范化（后处理，§4.2 Post-process）：
  - 回答正文中按 `[来源: 产品手册.pdf P12]` 标注
  - 回答末尾输出「参考来源」汇总列表：`文件名 + 页码 + 该来源引用的片段摘要（≤50 字）`
  - **同源合并**：同一文件多处引用合并为一个来源条目
- [x] 无检索结果分支（强化 Phase 1-06 的简易版）：
  - 阈值过滤后为空 → 走 `no_context` 模板
  - 检索有结果但模型判定与问题无关 → 允许模型说明未找到（prompt 授权）
- [x] 评估基线（`docs/eval/` 目录）：
  - 建立 10~20 条 QA 样例集：正常问答 / 无答案题 / 多来源题 / 追问题
  - `scripts/eval_run.py`：批量跑样例 → 输出回答 + 引用 → 人工记录质量评分（如 引用正确性 / 回答准确性 / 告知明确性 三档打分）
- [x] 结果沉淀：`docs/eval/results-{date}.md`，作为 Phase 3 优化的前后对比基线

## 3. 设计要点

- **模板用轻量方案**：`string.Template` 或 f-string 即可，不引入 Jinja2（模板少、变量固定）
- **引用格式即协议**：`[来源: 文件名 P页码]` 前后端共认（Phase 2-05 前端渲染成可点击的来源卡片）；格式变更必须前后端同步
- **来源片段摘要**：末尾汇总里的 snippet 从 chunk 元数据/正文截取，帮助用户快速确认引用是否相关（对齐 §9.1 界面中的 `[来源: 产品手册.pdf P12]`）
- **评估是工程任务**：样例集与脚本从本步骤开始建立，Phase 3 每个增强都跑同一套基线对比（改检索逻辑 → 重跑 → 看引用准确率变化）
- 提示词中不泄露内部实现细节（检索参数、阈值等），面向用户的问题定位保持中性

## 5. 验收标准

- [x] 引用格式统一：正文标注 + 末尾汇总列表；同一文件多处引用正确合并
- [x] 问无关问题 → 回答明确告知未找到，且不编造（与 Phase 1-06 行为对比有提升）
- [x] 样例集跑通：20 条样例全部有输出，无崩溃、无空响应
- [x] 记录一份评估基线结果（人工打分存档），标注日期与版本
- [x] 模板变更通过样例集回归（跑一遍确认无退化）

## 6. 风险与注意事项

- **引用幻觉**：模型可能在正文标注不存在的来源 —— 后处理校验：标注中出现的文件名必须存在于本次检索结果中，否则剔除并记录
- **评估主观性**：打分规则固定（三档制）、样例集固定，对比只看相对变化；不同人打分时口径不一致，尽量由同一人跑同批
- 模板改动是高频动作，每轮改动跑一遍样例集回归，避免"改一处坏一处"（样例集小，成本低）
