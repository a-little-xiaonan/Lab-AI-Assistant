## 1. 目标与范围

文档内容变更（或分块策略调整）后重建向量索引，且**重建期间线上检索不中断、失败不污染旧索引**。

## 2. 任务拆解

- [x] 接口：`POST /api/knowledge-bases/{id}/reindex`，请求体 `{doc_id?: string}`（缺省 = 全库重建）
- [x] 简单方案（先实现）：删除该文档旧 chunk → 重新走完整 pipeline（解析→清洗→分块→向量化→入库）
  - 状态流转：`ready → reindexing → ready / failed`（失败时旧索引已删，状态 failed，需用户重试）
- [x] **双 buffer 方案（推荐实现）**：
  - 新索引写入临时 collection（`kb_{id}_docs_new`）→ 全部成功后删除旧 collection 并改名 → 失败则丢弃临时 collection，旧索引完好
  - 检索期间读取的始终是旧 collection，重建全程检索不中断
- [x] 进度上报：全库重建时记录处理进度（当前文档 / 总数），接口 `GET /api/knowledge-bases/{id}/reindex/status` 返回（或复用文档状态列表）
- [x] 索引前后对比：重建完成后记录 chunk 数变化（`docs_before / docs_after`），前端展示
- [x] 前端联调：Phase 3-04 的「重新索引」按钮 + 进度展示 + 完成后刷新列表

## 3. 设计要点

- **buffer 方案优先级高**：删除即重建的简单方案在重建期间检索为空，知识库大了体验很差；双 collection 只多一次 `collection.rename`（或复制元数据），成本可接受
- **重建期间锁定**：同一文档/全库的重建任务互斥（进程内锁），重复触发直接返回"进行中"
- **失败语义**：buffer 方案下失败 = 丢弃临时 collection + 状态回 `ready`（旧索引仍在）+ `error_message` 记录；绝不出现"索引一半"的中间态
- 重新索引的触发场景：文档内容变更（重新上传同名文件）、分块参数调整（chunk_size 等，改动后需全库重建）、embedding 模型切换（同上）
- 重建走与首次上传**完全相同的 pipeline 函数**，禁止复制逻辑（唯一差异是写入目标 collection）

## 5. 验收标准

- [x] 修改源文件内容后重新索引 → 检索结果反映新内容（旧内容不再出现）
- [x] buffer 方案：重建进行中发起检索 → 返回的是旧索引结果（不中断、不报错）
- [x] 人为注入解析失败（损坏文件参与重建）→ 重建失败，旧索引完好，状态与错误信息可读
- [x] 重复触发重建 → 第二次返回"进行中"，不并发执行
- [x] 重建完成后 chunk 数对比可见（前端展示）

## 6. 风险与注意事项

- **ChromaDB 的 collection 改名支持**：不同版本能力不一（0.4 无 rename 需手动迁移），实现前先验证；退化方案：临时 collection 写入完成后，用一次「删旧 + 数据复制」的短事务完成切换
- **全库重建耗时**：大库重建以分钟计，进度上报是必须项；期间 token/embedding 调用量放大（计费观察）
- **重建与上传并发**：同一文档同时被「上传覆盖」与「重建」操作时，以任务锁串行化，避免双写
- 文档重新上传（覆盖）与 reindex 的关系：重新上传本身可触发自动重建（Phase 2-02 已有状态机），reindex 接口服务的是「无新文件、仅重算」的场景
