> **所属阶段**：Phase 3 — 高级功能

## 1. 目标与范围

对用户问题做 LLM 改写，扩展为多条检索查询（多查询策略），提升召回率。对齐 §6.2 示例：`"千问的定价是多少？"` → `["通义千问 API 价格", "千问模型收费标准", "DashScope 计费方式"]`。

## 2. 任务拆解

- [x] `app/core/query_rewrite.py`：
  - `rewrite(query) -> list[str]`：LLM 改写，返回 1 条原查询 + 2~3 条改写（扩展同义词、拆分子问题、补全领域术语）
  - prompt 明确约束：「仅输出检索查询列表，每行一条，不要解释」—— 输出格式错误时降级（见设计要点）
- [x] `rag_pipeline` 接入：
  - 检索环节改为：多查询 → 并发检索（asyncio.gather）→ 结果合并
  - **合并去重**：按 `(doc_id, chunk_index)` 去重，分数取 max；合并后仍按 `max_context_tokens` 截断
- [x] 配置开关：`REWRITE_ENABLED`（默认开）、`REWRITE_QUERY_COUNT=3`
- [x] 效果对比：用 Phase 2-04 的样例集分别跑 开/关 两轮，记录召回变化（重点看原先检索为空的题目是否被改写救回）

## 3. 设计要点

- **改写失败降级**：LLM 输出解析失败（非列表/为空）→ 直接用原查询检索，主链路永不因改写而中断
- **并发检索**：3 条查询并发检索，总延迟 ≈ 单次检索（多查询的额外成本主要是那一次改写调用）
- **改写只服务于检索，不替换原始问题**：发给 LLM 的最终 prompt 始终用**用户原始问题**（改写结果只进检索器），保证回答贴合用户原意。混合检索（Phase 3-06）下：改写查询喂**向量侧**，关键词侧默认只用原始问题词（词面精确优先，可配置扩展）
- 改写 prompt 面向「知识库检索」而非「闲聊」：要求输出知识库中可能出现的表述方式（术语、别名、产品名全称等）
- 与 Re-ranking（Phase 3-02）协同：改写提升召回（recall），重排提升精度（precision），两者独立开关

## 5. 验收标准

- [x] 输入 `"千问的定价是多少？"` → 输出 ≥ 3 条查询，其中包含「API 价格 / 收费标准 / 计费方式」类改写（对齐 §6.2 示例）
- [x] 改写后的多查询召回结果包含原查询检索不到的片段（样例集里至少 1 题验证）
- [x] 改写接口异常（mock 失败）→ 自动降级为原查询，回答正常
- [x] 开关切换行为正确：`REWRITE_ENABLED=false` 时行为与 Phase 2 完全一致
- [x] 样例集对比记录归档（开/关各一份）

## 6. 风险与注意事项

- **改写引入噪声**：改写可能跑偏（检索到无关内容）—— 靠阈值过滤（0.3）兜底，观察对比结果若噪声 > 收益则调低改写数量或改回单查询
- **额外成本**：每次提问多一次 LLM 调用（改写）+ 2 次检索调用；QPS 与计费需观察（附录 B 限流风险）
- 改写 prompt 中的示例（few-shot）要与实际领域匹配，通用示例在中文技术问答场景效果有限
