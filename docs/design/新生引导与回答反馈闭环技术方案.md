# 新生引导与回答反馈闭环技术方案

> **文档状态**：待实施设计
> **适用对象**：未登录访客、已注册新生、实验室内容管理员
> **核心目标**：让新生不仅能“提问”，还能够按兴趣完成实验室了解、报名准备和方向选择；同时把无答案、错误和过期资料转化为可审核的知识库改进任务。

## 1. 要解决的问题

纯聊天入口要求新生先知道“应该问什么”，实际会出现：

- 第一次进入页面，不知道实验室有哪些方向和招新流程；
- 同一个问题被大量重复询问，但知识库负责人看不到需求趋势；
- 回答不准确或资料已过期时，用户只能离开，问题不会进入修正流程；
- AI 自动修改知识库风险过高，可能把错误反馈直接变成新错误；
- 访客身份不稳定，不能把不同访客的会话和记忆混在一起。

本方案增加两个相互连接的能力：

```text
新生引导：帮助用户完成“了解 → 匹配方向 → 准备报名”
                              ↓
回答反馈：把真实问题与缺口送入“AI 建议 → 管理员审核 → 发布 → 回归评测”闭环
```

## 2. 新生引导流程

### 2.1 首次进入

首页不直接展示空白聊天框，而是先提供四类入口：

1. **了解实验室**：简介、老师、研究方向、成果和环境；
2. **了解招新**：面向对象、报名方式、培训、考核和时间安排；
3. **选择方向**：前端、后端、AI、数据分析、移动端等方向介绍；
4. **加入后能做什么**：项目、比赛、课程、导师和学长学姐指导。

每个入口本质上是一组经过审核的引导问题，不直接写死回答。点击后仍通过当前权限校验和 RAG 链路生成最新答案。

### 2.2 可选新生画像

登录用户可以自愿填写：

```text
专业、年级、已有基础、感兴趣方向、每周可投入时间、主要目标
```

这些信息用于推荐问题和调整回答顺序，不作为录取判断，也不向其他用户展示。字段必须支持跳过、修改和删除；未明确同意时不从聊天中自动推断敏感画像。

访客不建立跨会话长期画像，只使用独立的匿名会话标识维持当前浏览器中的短期上下文。匿名标识必须随机生成并设置较短有效期，不能让所有访客共享同一个会话。

### 2.3 引导阶段

建议将新生引导设计为可跳过的进度卡：

```text
阶段 1：认识实验室
阶段 2：了解技术方向
阶段 3：了解培养与项目
阶段 4：确认招新要求
阶段 5：生成个人准备清单
```

系统只记录“是否查看过某主题”，不把浏览进度伪装为能力评价。生成准备清单时，必须区分：

- 知识库中明确规定的事实；
- 根据用户自愿画像生成的个性化建议；
- 当前资料没有说明、需要咨询管理员的事项。

### 2.4 推荐逻辑

首期不需要额外训练推荐模型，采用可解释规则：

```text
用户兴趣/已读主题/未完成阶段
          ↓
从管理员配置的引导问题池中过滤
          ↓
按优先级、时效性和去重规则返回 3～5 条
```

推荐失败或画像为空时，回退到管理员维护的通用热门问题，不影响正常聊天。

## 3. 回答反馈设计

### 3.1 用户可以反馈什么

每条助手回答提供轻量反馈：

- 有帮助；
- 没有帮助；
- 信息不准确；
- 信息已过期；
- 回答不完整；
- 没有回答我的问题；
- 内容不适合公开；
- 其他说明。

“有帮助/没有帮助”一键即可提交；负向反馈再选择原因并可填写补充说明。不得强制用户提供个人信息。

### 3.2 反馈必须关联检索现场

只保存用户看到的回答不够，管理员还需要知道当时系统用了什么。每条反馈应记录：

```text
user_id / anonymous_id
session_id / message_id
原问题、最终回答
可访问知识库集合
召回 chunk_id、排名、相似度、重排分
证据门槛判定及拒答原因
模型、Prompt 版本、检索配置版本
反馈类型、备注和创建时间
```

Chunk 正文不重复写入反馈表，只保留 ID 和不可变版本号，避免数据膨胀；管理员查看时再按权限读取快照。

### 3.3 数据表

```text
answer_feedback
- id
- user_id                 可空
- anonymous_id            可空
- session_id
- message_id
- rating                  helpful / unhelpful
- reason                  inaccurate / outdated / incomplete / no_answer / privacy / other
- comment
- status                  new / triaged / resolved / dismissed
- assigned_to
- created_at
- resolved_at

answer_traces
- id
- message_id
- query_text
- kb_ids_json
- retrieved_chunks_json
- evidence_decision_json
- model_name
- prompt_version
- retrieval_version
- latency_ms
- created_at

knowledge_improvement_tasks
- id
- feedback_id
- task_type               add_document / update_document / fix_metadata / tune_retrieval / no_action
- ai_proposal_json
- reviewer_id
- review_status           pending / approved / rejected
- resolution_note
- created_at
- reviewed_at
```

反馈正文中可能包含手机号等信息，仍需经过敏感信息过滤，并沿用用户数据删除策略。

## 4. AI 初稿 + 管理员审核闭环

AI 不能根据一次负向反馈直接修改知识库。正确流程是：

```text
用户提交负向反馈
   ↓
系统聚合同类问题并创建改进任务
   ↓
AI 分析原问题、回答、检索结果和当前文档
   ↓
输出“问题原因 + 建议修改 + 建议来源”的草稿
   ↓
editor/admin 审核
   ├─ 驳回：记录理由
   ├─ 调整：人工编辑草稿
   └─ 批准：生成文档新版本
                 ↓
         数据治理审核与重新索引
                 ↓
       固定 QA 回归通过后关闭任务
```

AI 建议只能包括以下受控动作：补充文档、修改已有版本、修正主题、调整术语映射、增加评测问题或标记无需处理。它不能直接执行删除、降低访问级别或发布。

## 5. 无答案问题的特殊闭环

当证据门槛拒答时，系统内部记录 `no_answer` 事件，但不自动创建大量重复任务。按归一化问题和主题聚合：

- 同类问题在 7 天内出现 3 次以上，创建高优先级知识缺口；
- 只出现一次的问题进入观察列表；
- 明显与实验室无关的问题标记 `out_of_scope`，不要求补资料；
- 涉及个人名单、密码、内部联系方式等问题标记 `should_not_answer`，作为正确拒答而不是知识缺口。

管理员处理知识缺口时，可以一键把该问题加入正式 QA 评测集，防止后续修改再次退化。

## 6. 权限与隐私

| 操作 | guest | student | editor | admin |
| --- | ---: | ---: | ---: | ---: |
| 提交回答反馈 | ✓ | ✓ | ✓ | ✓ |
| 查看自己的反馈处理状态 | 匿名会话期内 | ✓ | ✓ | ✓ |
| 查看聚合统计 |  |  | 授权知识库 | ✓ |
| 查看问题原文和检索轨迹 |  |  | 授权知识库且脱敏 | ✓ |
| 创建/处理知识改进任务 |  |  | 授权知识库 | ✓ |
| 批准发布、修改权限级别 |  |  |  | ✓ |

安全要求：

- 检索轨迹的查看权限不能高于所涉及知识库；
- 面向管理员的统计默认聚合，不展示不必要的用户身份；
- 访客反馈以随机 `anonymous_id` 隔离，不能使用公共固定用户 ID；
- 用户删除账号时，按策略匿名化或删除其画像、反馈身份关联和长期记忆；
- 管理员不得从反馈内容推断或导出与招新无关的个人画像。

## 7. API 设计

### 7.1 新生引导

```text
GET  /api/onboarding/topics
GET  /api/onboarding/recommendations
GET  /api/onboarding/progress
PUT  /api/onboarding/progress
GET  /api/profile/onboarding
PUT  /api/profile/onboarding
DELETE /api/profile/onboarding
```

### 7.2 回答反馈

```text
POST /api/messages/{message_id}/feedback
PUT  /api/messages/{message_id}/feedback
GET  /api/me/feedback
GET  /api/admin/feedback
POST /api/admin/feedback/{id}/triage
POST /api/admin/feedback/{id}/resolve
POST /api/admin/improvement-tasks/{id}/ai-proposal
POST /api/admin/improvement-tasks/{id}/approve
POST /api/admin/improvement-tasks/{id}/reject
```

同一用户对同一回答只保留一条当前反馈，修改时保留审计记录，防止重复点击污染统计。

## 8. 管理端工作台

管理端至少包含四个视图：

1. **概览**：回答量、拒答率、帮助率、负向反馈率、P95 延迟；
2. **知识缺口**：按频次、用户角色、主题和时间聚合的无答案问题；
3. **待处理反馈**：可查看脱敏后的问题、回答和检索诊断；
4. **改进任务**：AI 草稿、人工审核、文档版本、重新索引和回归结果。

管理员修复后，系统应自动定位受影响的反馈并通知“资料已更新”；访客仅在匿名会话仍有效时可见，不发送外部消息。

## 9. 指标体系

用户体验指标：

- 引导完成率、各阶段退出率；
- 引导问题点击率和转化为实际提问的比例；
- 回答有帮助率、负向反馈率；
- 无答案率、无答案问题重复率；
- 新生从首次访问到完成报名准备清单的比例。

知识改进指标：

- 负向反馈平均首次处理时间；
- 知识缺口从发现到发布的平均时间；
- AI 建议被管理员采纳的比例；
- 修复后对应 QA 的通过率；
- 同类问题修复后的重复负反馈下降幅度。

工程指标：

- 反馈写入成功率；
- 检索轨迹采样率与存储量；
- 各角色越权访问拦截率；
- 反馈聚合任务失败率；
- 新版本发布后评测回归耗时。

## 10. 逐层兜底策略

| 环节 | 正常路径 | 失败时兜底 |
| --- | --- | --- |
| 引导配置 | 管理员配置主题与问题池 | 配置损坏时显示通用热门问题，聊天仍可用 |
| 用户画像 | 用自愿填写信息做个性化推荐 | 用户跳过或读取失败时使用匿名通用推荐 |
| 回答反馈 | 关联 message_id 和完整诊断轨迹 | 轨迹缺失时仍保存反馈，并标记 diagnostics_missing |
| AI 问题分析 | 生成原因和修复建议草稿 | 调用失败时创建人工任务，不阻断反馈提交 |
| 相似问题聚合 | Embedding + 规则聚类 | 向量服务失败时按归一化文本精确聚合 |
| 文档修复 | 生成新版本并走审核 | 修复失败保留当前发布版本，不影响线上问答 |
| 重新索引 | 双 Buffer 原子切换 | 失败继续使用旧索引，任务保留为待重试 |
| 回归评测 | 运行固定 QA 与知识缺口样例 | 评测失败或关键指标下降时禁止发布新版本 |
| 通知用户 | 登录用户站内提示 | 通知失败不回滚知识修复，只记录重试任务 |

## 11. 实施顺序

1. 给助手消息增加不可变 `message_id`，落库回答诊断轨迹；
2. 实现点赞/点踩和原因选择，先完成数据采集；
3. 建立管理端反馈列表、知识缺口聚合和处理状态；
4. 增加 AI 修复建议，但坚持人工审核后才能创建文档新版本；
5. 把修复流程接入文档治理、重索引和正式 QA 回归；
6. 最后实现新生引导主题页、自愿画像、进度与个性化推荐。

## 12. 验收标准

- 未登录访客之间的会话、反馈和推荐状态完全隔离；
- 每条反馈都能追溯到回答、问题、模型版本和当时的候选 Chunk；
- 用户提交反馈的主接口不依赖 AI，模型故障时仍可成功提交；
- AI 建议未经管理员批准不能修改文档、索引或访问级别；
- 知识缺口修复后必须新增回归样例，关键指标下降时阻止发布；
- 管理员只能查看其授权知识库的反馈详情，越权率为 0；
- 用户可以查看、修改或删除自己的引导画像；
- 系统能统计“哪些问题最常被问、哪些问题无法回答、哪些资料最需要更新”。
