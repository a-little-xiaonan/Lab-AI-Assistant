# P2：版本、权限隔离与模板失效方案

> 状态：已实施；在 P1 公开模板基础上增加角色等级、版本化命名空间与失效事件。
> 适用范围：将 FAQ 模板从公开资料扩展到学生、编辑等分级知识库时的安全边界。

## 1. 目标

保证资料更新、发布状态变化或用户权限变化后，系统绝不以旧模板回答，也绝不向不具备权限的用户复用含非公开资料的固定前缀。

P2 的核心不是主动删除供应商的短期 KV Cache，而是通过严格的模板可用性校验与版本化前缀，让旧缓存无法被新请求命中。

## 2. 隔离原则

1. **鉴权先于模板选择**：只在 `list_readable_kbs()` 得出服务端可读范围后查询模板。
2. **按内容权限隔离，而非按用户 ID 隔离**：同一公开模板可被不同用户复用；含学生资料的模板只可被满足学生范围的用户使用。
3. **模板证据不可跨范围混合**：一个模板只能对应一个确定的 `audience_scope` 和证据范围。
4. **运行时最终校验**：不能只依赖发布时任务，调用前必须核验文档、版本、有效期和权限。
5. **默认拒绝**：DB 查询、快照计算或权限校验失败时，模板路径不可用，转入现有 RAG 的安全路径。

## 3. 模板可用性签名

模板调用前计算或读取如下签名：

```text
cache_namespace = hash(
  model_id,
  provider_protocol_version,
  template_code,
  template_version,
  prompt_policy_version,
  audience_scope,
  template_kb_scope_and_level,
  knowledge_snapshot,
  tool_schema_version
)
```

该签名中的内容必须同时写进稳定 Prompt 前缀。任何一个维度变化都会导致前缀不同，从而自然隔离旧 KV 状态。

实现使用模板自身的排序知识库 ID 与等级（`template_kb_scope_and_level`），而不是用户完整可读范围；因此同一 `student` 模板可安全复用于所有满足学生等级的用户，且不写入用户个人身份、姓名或学号。模板证据所在知识库与文档敏感等级必须和 `audience_scope` 完全一致，禁止混合等级证据。

## 4. 失效事件

以下事件必须让关联模板从 `active` 变为 `stale`，并记录审计事件：

| 事件 | 处理 |
| --- | --- |
| 新版本发布或回滚 | 失效引用该 `doc_id` 的模板 |
| 文档归档、删除、过期 | 失效引用该 `doc_id` 的模板 |
| 文档有效期变更 | 失效引用该 `doc_id` 的模板 |
| 知识库访问级别变化 | 失效该知识库全部模板 |
| 权限策略版本变化 | 失效受影响 audience scope 的模板 |
| Prompt 规则或工具定义变化 | 递增规则版本，旧模板不可命中 |

失效处理应与现有发布事务衔接：发布成功后再标记模板 stale；发布失败保持旧文档和旧模板继续服务。模板重建不是自动发布，必须经过资料与权限复核。

## 5. 运行时验证

`template_validator.validate(template, user, readable_kbs)` 至少执行：

1. 模板状态为 `active`；
2. `audience_scope` 不高于当前用户实际权限；
3. 模板 `audience_scope` 不高于当前用户等级，且模板 KB 范围是当前可读 KB 范围的子集；
4. 每条 Evidence 对应文档仍为 `ready`、`published`、未删除且在有效期内；
5. Evidence 的 `document_version_id` 仍等于文档当前发布版本；
6. 根据当前版本重新计算的 `knowledge_snapshot` 与模板保存值一致；
7. `stable_prompt_hash` 与实际将发送的稳定部分一致。

任一检查失败时记录结构化原因，例如 `template_stale`、`template_scope_denied`、`template_snapshot_mismatch`，不发送缓存 Prompt。

## 6. 管理流程

```text
管理员创建草稿模板
  → 选择已发布 Chunk 作为证据
  → 系统计算证据快照与稳定 Prompt hash
  → 权限管理员复核 audience scope
  → 模板 active

资料或权限发生变化
  → 关联模板 stale
  → 管理员基于新发布 Chunk 重建/审核
  → 新 template_version active
```

P2 不新增管理端页面。模板仍由管理员本地导入；发布成功、归档、治理信息更新和知识库删除时，会在原有事务中将关联活跃模板标记为 `stale`，并将模板 ID 写入原操作的审计详情。模板重建后才可再次激活。

P2 迁移会把早期 `public` 受众统一为 `guest`，并将所有旧的 `active` 模板置为 `stale`：这是因为稳定前缀新增了受众与缓存命名空间，旧哈希不得继续复用。

## 7. 测试与验收

必须覆盖以下端到端案例：

- 访客访问公开模板成功；
- 访客不能命中学生模板，且不会获得其 `sources`；
- 学生可命中学生模板，编辑/管理员不因更高权限而复用低范围外的混合模板；
- 文档发布新版本后，旧模板立即失效并回退 RAG；
- 文档过期时，模板不可用；
- 文档发布失败时，旧模板不被错误失效；
- 模板校验数据库异常时 fail closed。

验收门槛为：任何未经授权模板命中、任何失效模板回答或任何跨范围 source 暴露均为阻断缺陷。

## 8. 风险与回退

- **失效事件漏接**：运行时快照终检作为第二道防线；无法校验则禁用模板路径。
- **权限范围过粗**：P2 初期仅允许 public/student/editor/admin 四档，复杂的用户特例授权暂不进入缓存模板。
- **模板维护成本高**：只为日志证明高频且内容稳定的问题建立分级模板；低频问题继续用普通 RAG。
- **供应商缓存不可控**：版本签名只控制应用是否发送相同前缀，不依赖供应商提供缓存删除接口。
