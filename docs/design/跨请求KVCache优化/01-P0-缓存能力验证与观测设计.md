# P0：模型 Context Cache 能力验证与观测设计

> 状态：已实施；缓存命中能力已验证，但当前 POC 未通过 TTFT 收益门槛，P1 暂不启动。
> 适用范围：实验室 AI 助手的 DashScope 生成调用；本阶段不改变 RAG 问答路径、不引入 FAQ 模板。

## 1. 目标

先验证当前业务空间、模型和调用协议是否能够产生可观测的 Context Cache 命中，再决定是否投入 FAQ 模板改造。该阶段只增加受控 POC 与指标能力，不向真实用户流量启用缓存分支。

本项目当前的 `backend/app/llm/qwen.py` 通过 DashScope `Generation.call` 调用 `qwen-plus`。现有封装只读取回答文本，不保留供应商 `usage` 中可能出现的缓存 Token 信息；`rag_pipeline.py` 只记录检索与生成总耗时，也未记录首 Token 延迟。因此不能以“支持流式输出”推断已获得 KV Cache 收益。

## 2. 原理与判定口径

Transformer 生成前会对输入 Prompt 进行 Prefill，计算各层 Key/Value。若后续请求的前缀完全相同，模型服务可以重用这一段的 KV 状态，只计算后缀中变化的内容。缓存复用的是计算状态，不是旧答案；每个问题仍需要重新生成回答。

```text
首次：固定前缀 P + 动态后缀 S1 → 计算 P、S1 → 生成
后续：固定前缀 P + 动态后缀 S2 → 复用 P 的状态、只计算 S2 → 生成
```

百炼的缓存能力、支持模型和字段名称需以实际调用响应及官方控制台为准。POC 的成功条件不是“请求未报错”，而是同一稳定前缀的后续请求中出现正数 `cached_tokens`（或等价字段），并且热请求 TTFT 相对冷请求有统计意义上的下降。

## 3. POC 输入设计

构造一个不少于当前供应商门槛的固定前缀，内容由以下部分组成：

1. 固定回答规则；
2. 无敏感信息的模拟招新资料卡；
3. 固定的引用映射说明；
4. 变化的用户问题作为最后一个消息或缓存标记之后的内容。

不得在固定前缀内放入当前时间、request_id、用户名、会话历史、随机排序结果或动态检索结果。前缀必须以同一模型、同一业务空间、同一消息角色顺序和同一字符内容重复发送。

测试至少发送三类请求：

| 组别 | 前缀 | 后缀 | 目的 |
| --- | --- | --- | --- |
| 冷启动 | P | S1 | 建立缓存或取得基准耗时 |
| 热命中 | P | S2 | 验证缓存 Token 与 TTFT |
| 破坏前缀 | P' | S3 | 确认内容变化后不会误判命中 |

如显式缓存需改用 OpenAI 兼容协议或消息缓存标记，应只在新增的适配器中切换，不直接替换现有 `qwen.py` 的普通生成实现。

## 4. 拟修改范围

确认实施时，修改范围限制如下：

| 位置 | 变更 |
| --- | --- |
| `backend/app/llm/qwen.py` | 新增缓存能力适配器、提取非流式与流式最终响应中的 usage；既有 `chat_completion*` 行为不变 |
| `backend/scripts/smoke/` | 新增本地 `smoke_context_cache.py`，只使用模拟资料卡 |
| `backend/app/config.py` | 增加关闭状态的 POC 开关、模型/协议配置；默认不影响生产请求 |
| `backend/tests/` | 用 SDK Mock 覆盖 usage 解析、冷/热/前缀变化的指标计算 |

不新增数据库表、不修改聊天 API、不向用户问题注入任何真实内部资料。

## 5. 指标与日志

每次 POC 记录以下脱敏指标：

```text
model、protocol、prompt_prefix_hash、input_tokens、cached_tokens、
cache_creation_tokens、ttft_ms、end_to_end_ms、status、error_code
```

TTFT 定义为服务端开始调用模型到收到第一个非空文本增量的时间。它不同于总生成耗时，也不同于 SSE `meta` 帧发送时间。

日志不能记录原始用户问题、完整 Prompt、资料正文或 API Key。`prompt_prefix_hash` 仅用于验证前缀是否稳定。

## 6. 验收与决策

满足以下条件才进入 P1：

- 同一前缀的热请求可观测到供应商缓存命中；
- 热请求 TTFT 在重复样本中优于冷请求，且未明显拉高端到端 P95；
- 产生缓存命中的模型、地域、SDK/协议和 usage 字段均被记录；
- 普通生成路径的单元测试与冒烟测试保持通过。

出现以下任一情况则停止后续开发：模型不支持、可用前缀不足以触发缓存、同一 5 分钟窗口内重复率过低，或缓存创建成本高于可验证收益。停止后仅保留 POC 记录，不影响现有 RAG。

## 7. 实施结果（2026-10-03）

已新增默认关闭的 POC 配置、显式缓存消息构造、缓存用量/TTFT 解析、模拟公开资料冒烟脚本和单元测试。真实调用使用配置中的 `qwen3.8-flash`，固定前缀为 3,889 输入 Token 左右；每轮通过改变前缀的第一个内容块隔离冷启动，随后使用相同前缀发送热请求。

| 指标 | 冷请求 | 热请求 |
| --- | ---: | ---: |
| 样本数 | 3 | 3 |
| 缓存命中率 | 0% | 100% |
| 命中/创建缓存 Token | 创建约 3,872 | 命中约 3,872 |
| TTFT P50 | 3.12s | 3.55s |
| TTFT P95 | 3.53s | 4.99s |

结论：显式缓存标记、供应商用量字段和冷/热隔离均工作正常，但本次小样本中热请求 TTFT 未改善，反而高于冷请求。网络与模型调度波动可能影响单次流式首包，现有数据不足以将收益归因于缓存。因此保持 `CONTEXT_CACHE_POC_ENABLED=false`，不接入聊天主链路，也不进入 P1 公开 FAQ 模板阶段。

验证情况：`tests/test_qwen_stream.py` 9 项通过，`compileall` 通过。完整 `pytest tests -q` 中有 6 个既有聊天/Agent 用例因沙箱阻止 MySQL 与 DashScope 外部连接而失败；该失败与 P0 代码无关，未作为通过结论。

## 8. 风险与回退

- **协议不兼容**：将显式缓存封装为可选 adapter，失败时回退既有 DashScope 调用。
- **误把偶发延迟当收益**：冷/热请求交替多轮执行，按 P50/P95 观察，不能只展示单次最佳值。
- **成本失控**：POC 使用固定次数和模拟文本；不做定时预热。
- **缓存含敏感信息**：P0 不使用真实内部资料；P1 也只允许公开资料。
