# 01 / M0：数据库迁移与权限收口

> 状态：已执行（2026-09-07）
>
> 前置依赖：当前用户、角色、JWT、知识库等级权限已可运行
>
> 后续依赖：02～07 全部任务包

## 1. 本阶段目标

本阶段不增加面向用户的新业务能力，而是为后续数据库扩展和内容审核建立可靠地基：

1. 使用 Alembic 管理数据库结构变化，替代持续堆叠手写 `ALTER TABLE`；
2. 将所有权限判断收口到统一资源—操作授权服务；
3. 确认 `access_level` 是知识库授权的唯一事实源；
4. 为每个请求生成 `request_id`；
5. 建立最小可用审计服务，先覆盖关键高风险操作。

## 2. 范围边界

本阶段包含：

- Alembic 初始化、基线和首个迁移；
- 权限 action 定义与路由接入；
- 旧 ACL 数据盘点和接口退役；
- request_id 中间件；
- 审计服务基础接口。

本阶段不包含：

- 文档审核状态和版本表；
- 成员申请业务；
- Redis、RQ；
- 新增管理后台业务页面；
- 树形意图分类器。

## 3. 当前问题

当前项目虽然已经实现 `guest < student < editor < admin`，但仍存在以下风险：

- `knowledge_base_role_permissions`、`knowledge_base_user_permissions` 与 `access_level` 并存，容易产生“配置成功但检索不生效”；
- 不同接口可能直接判断角色字符串，后续增加操作时容易漏鉴权；
- `create_all()` 和 `_add_column_if_missing()` 缺少迁移版本、回滚和执行记录；
- `audit_logs` 只有表，没有统一调用入口；
- 日志无法稳定串联同一次 HTTP 请求的全过程。

### 4.3 决策入口

新增统一接口：

```python
authorize(actor, action, resource=None) -> AuthorizationDecision
require_action(action, resource_loader=None)
list_readable_kbs(actor) -> list[str]
```

`AuthorizationDecision` 至少包含：

```text
allowed
reason_code
actor_role
resource_level
```

实施规则：

1. API 路由用 `Depends(require_action(...))`；
2. 会话和长期记忆额外校验资源所有者；
3. RAG 检索入口只接收后端计算出的可读知识库，不信任前端传入范围；
4. 用户被禁用时优先拒绝所有受保护操作；
5. 前端路由守卫只控制显示体验，后端仍必须独立鉴权；
6. 新增 action 前不得在业务代码中继续添加零散角色判断。

## 5. 数据库迁移方案

### 5.1 引入 Alembic

新增：

```text
backend/alembic.ini
backend/alembic/env.py
backend/alembic/script.py.mako
backend/alembic/versions/<baseline>.py
backend/alembic/versions/<m0>.py
```

执行顺序：

1. 备份 MySQL 数据库；
2. 备份 `data/chroma`；
3. 配置 `Base.metadata` 为 Alembic `target_metadata`；
4. 对现有数据库执行 baseline stamp，不重新创建旧表；
5. 生成 M0 迁移，补齐审计和后续阶段需要的兼容字段；
6. 本地验证 upgrade、downgrade、再次 upgrade；
7. 启动脚本在应用启动前执行 `alembic upgrade head`。

约束：

- 迁移脚本不得从 `.env` 之外获取数据库凭据；
- 日志不得打印完整数据库 URL；
- 生产/演示环境迁移失败时必须停止启动；
- 暂时保留旧手写迁移，仅用于兼容一次，确认 Alembic 生效后移除。

### 5.2 旧 ACL 收口

第一步只读盘点：

```sql
SELECT COUNT(*) FROM knowledge_base_role_permissions;
SELECT COUNT(*) FROM knowledge_base_user_permissions;
```

默认处理：

1. 如两表为空，从前端和 OpenAPI 移除授权入口；
2. 旧接口在一个兼容版本内返回 `acl_deprecated`；
3. 所有实际权限只调用 `authorize()`；
4. 下一次迁移再删除旧表，避免直接误删未知数据。

若两表存在有效数据，则暂停删除，先导出清单并人工决定如何映射到 `access_level`。

## 6. request_id 与审计基础

### 6.1 request_id

新增 HTTP 中间件：

- 接收合法的 `X-Request-ID`，否则生成 UUID；
- 写入 `request.state.request_id`；
- 响应头返回 `X-Request-ID`；
- 日志格式自动携带 request_id；
- 不使用用户输入的超长或非法 request_id。

### 6.2 审计接口

新增 `backend/app/services/operations/audit.py`：

```python
record_in_transaction(db, actor, action, resource, detail)
record_best_effort(actor, action, resource, detail)
```

M0 先覆盖：

```text
auth.login.success
auth.login.failed
user.role.update
user.status.update
kb.create
kb.update
kb.delete
document.upload
document.delete
```

审计详情禁止记录密码、JWT、Refresh Token、API Key、完整 Prompt、用户私人记忆和数据库 URL。

## 9. 兜底与回滚

| 风险 | 兜底 |
| --- | --- |
| Alembic baseline 对不上现有库 | 停止迁移，使用备份恢复，不自动重建表 |
| 旧 ACL 表存在数据 | 只导出清单，不删除、不自动映射 |
| 新 policy 判断异常 | fail closed，拒绝访问并记录 reason_code |
| 审计 best-effort 写入失败 | 主业务继续，写应用错误日志 |
| 关键操作审计写入失败 | 与业务事务一起回滚 |
| request_id 非法 | 丢弃外部值并生成新 UUID |

## 10. 验收标准

- 数据库可从当前版本升级、降级并再次升级；
- 未登录、student、editor、admin 的结果符合角色矩阵；
- 被禁用用户无法通过旧 Token 调用保护接口；
- 用户不能读取或删除其他用户的会话和长期记忆；
- 前端伪造知识库 ID 无法越权检索；
- 旧 ACL 接口不会再制造“假授权”；
- 每个关键操作可按 request_id 在日志与审计表中关联；
- 既有后端测试通过，前端构建通过。
