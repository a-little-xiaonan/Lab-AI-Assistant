## 1. 本阶段目标

解决“注册用户如何成为实验室成员”和“高风险操作如何追溯”两个问题：

1. 注册用户默认只能获得 student；
2. 用户通过申请并由管理员审批后才能成为 editor；
3. admin 不能通过公开申请获得，只能由现有管理员人工授予；
4. 角色变化、文档发布、知识库删除等操作形成统一审计链路；
5. 系统后台提供申请审批和审计查询界面。

## 2. 范围边界

包含：

- 成员申请、撤销、批准和驳回；
- 角色变更事务；
- 统一审计 action 和查询；
- 登录、权限拒绝和高风险操作审计；
- 普通用户申请页与管理员审批页。

不包含：

- 自动根据邮箱或邀请码直接提权；
- 用户申请 admin；
- 上传身份证件等敏感证明材料；
- 组织、多租户和复杂审批流引擎。

## 3. 成员申请模型

新增 `role_applications`：

```text
id                    app_ 前缀 UUID
user_id
target_role           第一版固定 editor
reason
evidence_text         可选，仅允许普通文字
status                pending / approved / rejected / cancelled
reviewed_by
review_comment
created_at
updated_at
reviewed_at
```

数据库约束：

- 同一用户同时只能有一条 pending；
- target_role 第一版只允许 editor；
- reviewed_by 必须是有效 admin；
- approved/rejected 必须存在 reviewed_at；
- 历史申请不物理删除。

## 4. 业务规则

### 4.1 注册与申请

- 注册后默认 student；
- 请求体中的 role、roles、access_level 一律忽略或拒绝；
- student 可以申请 editor；
- editor 重复申请直接返回已具备权限；
- 被禁用用户不能提交申请；
- 用户可以撤销自己的 pending 申请。

### 4.2 审批

批准操作必须在同一事务中完成：

1. 锁定申请记录；
2. 确认仍为 pending；
3. 确认申请用户仍有效；
4. 写入或更新 `user_roles`；
5. 更新申请为 approved；
6. 写入关键审计日志；
7. 提交事务。

驳回必须填写原因。管理员不能批准自己的申请，虽然正常流程本身不允许 admin 提交申请。

### 4.3 权限生效

角色变更后下一次请求立即生效：

- Access Token 内不把角色作为长期可信事实；
- 鉴权依赖每次从数据库或短时缓存读取当前角色；
- 若使用角色缓存，审批成功后主动失效；
- 用户降级或禁用同样立即失效。

## 5. API 设计

用户侧：

```text
POST /api/users/me/role-applications
GET  /api/users/me/role-applications
POST /api/users/me/role-applications/{id}/cancel
```

管理员侧：

```text
GET  /api/admin/role-applications?status=pending&offset=0&limit=20
GET  /api/admin/role-applications/{id}
POST /api/admin/role-applications/{id}/approve
POST /api/admin/role-applications/{id}/reject
```

审计侧：

```text
GET /api/admin/audit-logs
GET /api/admin/audit-logs/{id}
```

审计列表支持：时间范围、actor、action、resource_type、resource_id、result 和 request_id 过滤，必须分页。

## 6. 审计模型与服务

扩展现有 `audit_logs`：

```text
request_id
actor_user_id
actor_role
action
resource_type
resource_id
result                success / denied / failed
reason_code
detail_json
ip_hash
user_agent_summary
created_at
```

统一服务：

```python
record_in_transaction(db, actor, action, resource, result, detail)
record_best_effort(actor, action, resource, result, detail)
```

必须同事务记录：

```text
user.role.update
user.status.update
role_application.approve
role_application.reject
kb.delete
document.publish
document.archive
document.rollback
```

允许 best-effort：

```text
auth.login.success
auth.login.failed
authorization.denied
retrieval.degraded
```

脱敏规则：

- IP 保存带服务端盐的哈希；
- User-Agent 只保留浏览器、系统和设备摘要；
- detail_json 不保存密码、Token、密钥、完整文档正文、完整 Prompt 和长期记忆正文；
- 登录失败不记录用户提交的密码。

## 10. 兜底与回滚

| 风险 | 兜底 |
| --- | --- |
| 重复提交 | 数据库唯一约束 + 业务 409 |
| 两个管理员同时审批 | 行锁或条件更新，只允许一个成功 |
| 角色写入成功但申请状态失败 | 同一事务整体回滚 |
| 审计写入失败 | 关键操作整体回滚 |
| 角色缓存未失效 | 权限服务回源数据库，缓存使用短 TTL |
| 用户伪造 target_role=admin | schema 和服务层双重拒绝 |
| 审计 detail 含敏感键 | 统一字段白名单和脱敏器过滤 |

## 11. 验收标准

- 新注册用户不能通过请求体获得 editor/admin；
- student 只能申请 editor；
- 同一用户不能存在两条 pending；
- 只有 admin 能批准和驳回；
- 批准后用户下一次请求可进入知识库工作台；
- 用户被降级后下一次请求立即失去管理权限；
- editor 无法访问申请审批和完整审计接口；
- 每个高风险操作可查到操作人、资源、时间、结果和 request_id；
- 审计内容不包含密码、Token 和私人记忆；
- 既有后端测试通过，前端构建通过。
