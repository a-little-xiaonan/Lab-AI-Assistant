## 1. 本阶段目标

把当前“上传成功后立即进入正式索引”改造成可信的内容供应链：

```text
上传 → 技术处理 → 自动检查 → AI 初标 → 成员预审
→ 管理员批准 → 双缓冲发布 → 正式检索
```

核心保证：未经审核、已过期、已归档或权限不匹配的资料，不能通过任何检索路径进入最终 Prompt。

## 2. 范围边界

包含：

- 文档技术状态与治理状态分离；
- 文档版本、质量检查和审核记录；
- AI 初标、editor 预审、admin 最终发布；
- 发布、归档、回滚统一触发正式索引更新；
- Prompt 前发布状态终检；
- 知识库工作台审核页面。

不包含：

- Redis/RQ 持久任务，先继续复用现有 BackgroundTasks；
- 成员申请；
- 自动把 AI 建议直接发布；
- 数千份资料场景的单文档差量原子切换。

## 3. 状态模型

### 3.1 技术处理状态

沿用 `documents.status`：

```text
processing → ready
           └→ failed
ready → reindexing → ready / failed
```

### 3.2 内容治理状态

新增 `documents.governance_status`：

```text
draft → pending_review → publishing → published
                      ├→ rejected
published → archived
rejected → draft
archived → publishing
任意有效状态 → deleted
```

只有以下条件同时满足才允许检索：

```text
status = ready
governance_status = published
knowledge_base.status = active
effective_at <= 当前时间
expires_at 为空或 expires_at > 当前时间
用户拥有 kb.read
```

## 5. 处理链路改造

### 5.1 准备阶段

将现有 `document_processing.process_document()` 拆出：

```python
prepare_document(document_id)
```

顺序：

1. 检查文件头、MIME、大小和扩展名；
2. 保存版本文件到隔离目录；
3. 专用解析器 → Unstructured → 文本试探；
4. 清洗和结构分块、递归固定分块；
5. Chunk 明细写入 MySQL；
6. 执行质量检查；
7. AI 给出主题、摘要、关键词、访问等级和风险建议；
8. 无阻断项则进入 `pending_review`；
9. 不调用 Embedding，不写正式 Chroma collection，不更新 BM25 正式索引。

### 5.2 发布阶段

新增：

```python
publish_knowledge_base(kb_id, candidate_document_ids)
```

顺序：

1. 锁定知识库发布任务；
2. 将待批准文档临时视为拟发布集合；
3. 查询全部有效 `published` 文档和本次批准版本；
4. 全量 Embedding 写入 `kb_{kb_id}_docs_new`；
5. 校验文档 ID、Chunk 数、向量维度和 collection 数量；
6. 调用现有 `swap_collections()`；
7. 提交文档发布状态、发布人和时间；
8. 从正式发布 Chunk 重建 BM25；
9. 保留 `docs_old`，下一次发布开始前清理。

发布失败时不改变旧正式索引，文档从 `publishing` 回到 `pending_review` 并记录错误。

### 5.3 检索终检

Chroma 返回候选后、进入 Prompt 前：

1. 收集候选 `doc_id`；
2. 批量查询 MySQL；
3. 过滤非 published、过期、归档、逻辑删除和越权文档；
4. 状态查询失败时 fail closed，本轮不把候选交给 LLM；
5. 所有候选被过滤后走“资料不足”回答。

## 6. 人工审核流程

1. editor 上传，文档进入 draft/processing；
2. 处理完成进入 pending_review；
3. editor 修正 AI 主题、摘要、有效期和访问等级；
4. editor 提交预审意见；
5. admin 查看原文、Chunk、风险项和版本差异；
6. admin 批准、驳回或退回修改；
7. 批准后异步发布，索引成功才标记 published。

管理员是否可以审核自己上传的资料由 `REVIEW_SEPARATION_ENABLED` 控制。第一版默认关闭职责分离，适应实验室人数较少的实际情况。

POST /api/knowledge-bases/{kb_id}/documents/{doc_id}/publish

所有写接口携带版本号或 `If-Match`，防止并发覆盖。只有 admin 可以执行最终发布、归档和回滚。

## 9. 旧数据迁移

为避免升级后知识库突然为空：

- 当前 `status=ready` 文档回填为 `governance_status=published`；
- `legacy_unreviewed=true`；
- `review_comment=历史数据迁移，待复核`；
- 当前 failed 文档回填为 draft，不进入检索；
- 管理后台展示历史待复核清单，由管理员逐批确认。

迁移前后分别记录 ready/published/failed 数量，数量不一致时回滚。

## 12. 兜底与回滚

| 环节 | 失败处理 |
| --- | --- |
| 文件安全检查 | 留在隔离区，标记 blocking，不解析 |
| 解析失败 | status=failed，保留可读错误，不生成向量 |
| AI 初标失败 | 标记未标注，由人工补充，不阻断审核 |
| 敏感扫描不确定 | 按高风险处理，禁止公开发布 |
| 审核并发冲突 | 返回 409，要求刷新后重新操作 |
| Embedding 失败 | 重试可恢复错误，最终失败保留旧索引 |
| docs_new 校验失败 | 删除临时 collection，不切换 |
| swap 失败 | 尝试恢复旧名称，文档回 pending_review |
| MySQL 状态终检失败 | fail closed，不向 LLM 提供候选 |

## 13. 验收标准

- 未审核文档不会进入 Chroma 正式 collection；
- 未审核文档不会进入 BM25 正式索引；
- 绕过前端直接调用检索也无法获取未发布内容；
- editor 不能最终发布、归档和回滚；
- admin 批准且索引成功后，回答才出现新来源；
- 发布失败时旧知识库仍可正常问答；
- 过期、归档和逻辑删除资料无法进入 Prompt；
- 上传人、审核人、发布人、版本和意见均可追溯；
- 既有后端测试通过，前端构建通过。
