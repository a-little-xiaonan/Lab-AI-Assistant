# 04 / M3：量化评测与数据治理

> 状态：已执行（2026-09-07）
>
> 前置依赖：02-M1 已验收
>
> 后续依赖：06-M5、07-最终验收

## 1. 本阶段目标

让系统具备两项能力：

1. 用固定、可复现的数据回答“检索和回答效果怎么样”；
2. 用自动检查、有效期和人工复核保证知识库内容持续可信。

本阶段完成后，简历中的 Recall、引用准确率、拒答准确率、延迟和成本必须能够由评测结果文件复现，而不是人工估计。

## 2. 范围边界

包含：

- 100+ 招新问题评测集；
- 检索、回答、性能和成本指标；
- 规则、LLM Judge 和人工抽检；
- 版本化评测运行和结果对比；
- 文档敏感、重复、过期、冲突和 Chunk 质量检查；
- 评测发布门禁。

不包含：

- 把建议目标冒充当前成绩；
- 用 holdout 样本调参；
- 自动发布 AI 生成或修订的知识；
- 生产级大规模监控平台。

## 3. 评测集设计

将 `docs/eval/recruitment-qa.json` 扩展到至少 100 条，格式统一为：

```json
{
  "id": "recruit-001",
  "category": "招新流程",
  "question": "大一新生怎么加入实验室？",
  "expected_answer_points": ["报名方式", "考核流程"],
  "expected_doc_ids": ["doc_xxx"],
  "expected_chunk_ids": [],
  "expected_topic_codes": ["recruitment"],
  "answerable": true,
  "difficulty": "normal",
  "split": "dev"
}
```

覆盖比例建议：

| 类型 | 建议数量 |
| --- | ---: |
| 直接事实 | 25 |
| 口语化、别名、术语 | 15 |
| 复杂多子问题 | 15 |
| 多轮追问与指代 | 15 |
| 多来源综合 | 10 |
| 明确不可回答 | 10 |
| 过期、冲突和权限边界 | 10 |

数据拆分：

- dev：约 70%，允许用于调参；
- holdout：约 30%，只在版本发布前运行；
- 所有 expected 字段由人工确认；
- 真实用户问题进入候选池后必须脱敏并人工审核。

## 4. 指标定义

### 4.1 检索指标

- `Recall@5`：标准来源至少一个进入前 5 的题目比例；
- `MRR@5`：第一个正确来源排名倒数的平均值；
- `nDCG@5`：多相关来源的排序质量；
- `Topic Route Recall`：主题定向路命中目标主题的比例；
- `Sub-question Coverage`：复杂问题的标准子问题中有证据支持的比例；
- `Empty Retrieval Rate`：应回答问题却无候选的比例。

### 4.2 回答指标

- `Answer Correctness`：标准答案要点覆盖率；
- `Groundedness`：回答中的事实能被引用 Chunk 支持的比例；
- `Citation Precision`：引用确实支持相应结论的比例；
- `Citation Coverage`：需要证据的结论中带有有效引用的比例；
- `No-answer Accuracy`：无答案时正确拒答、有答案时不误拒答；
- `Permission Safety`：测试用户无法从回答获得越权内容。

### 4.3 性能与成本

- 检索延迟 P50/P95；
- 首 Token 延迟 P50/P95；
- 完整回答延迟 P50/P95；
- Query Rewrite、Embedding、重排和生成调用次数；
- 每题输入/输出 Token；
- 单题估算成本；
- 错误率、降级率和超时率。

## 5. 评分方法

### 5.1 自动计算

使用 expected_doc_ids/chunk_ids 自动计算 Recall、MRR 和 nDCG；从运行埋点计算延迟、Token、成本和降级率。

### 5.2 LLM Judge

Judge 只接收：

```text
问题、标准要点、模型回答、实际引用文本
```

不得接收系统 Prompt、用户隐私记忆、API Key 或评测标签以外的信息。要求输出严格 JSON，解析失败时标记待人工评分，不补造分数。

### 5.3 人工抽检

- 每轮随机抽查至少 10%；
- 关键招新问题和权限边界题 100% 人工检查；
- 对 LLM Judge 与人工差异超过阈值的题重新评审；
- 人工评分者和时间写入结果。

## 6. 建议发布门禁

以下是首版目标，不是当前实测成绩：

| 指标 | 建议目标 |
| --- | ---: |
| Recall@5 | >= 85% |
| MRR@5 | >= 0.75 |
| Citation Precision | >= 95% |
| Groundedness | >= 90% |
| No-answer Accuracy | >= 90% |
| 权限泄漏题 | 0 例 |
| 关键招新问题错误 | 0 例 |
| 相比上一版单项下降 | 不超过 2 个百分点 |

最终阈值必须在第一次完整基线后确认。未达门禁的检索配置不得成为默认配置，但不阻止开发分支继续实验。

## 8. 数据治理规则

### 8.1 必填元数据

```text
内容负责人
资料来源
适用范围
主题
敏感等级
生效时间
过期时间
最后复核时间
```

默认复核周期：

- 招新时间、负责人、联系方式：180 天；
- 竞赛和成果统计：365 天；
- 实验室介绍和研究方向：730 天；
- 内部培训和项目资料：人工设置。

### 8.2 自动检查顺序

```text
文件头和 MIME
→ 大小与压缩安全
→ SHA-256 完全去重
→ 归一化文本 content_hash
→ 空内容、乱码和重复段落
→ 密钥、密码、手机号、学号、名单等敏感扫描
→ SimHash/MinHash 近重复
→ 日期、版本和矛盾内容提示
→ Chunk 长度、重复率和异常字符
```

### 8.3 阻断规则

- API Key、密码、JWT、数据库连接串：blocking；
- guest/student 资料出现手机号、学号和个人名单：默认 blocking；
- 文件格式伪装、压缩炸弹、空文档：blocking；
- 近重复、过期和冲突：needs_review，不自动删除；
- AI 判断不确定：只做风险提示，由人工决定。

### 8.4 过期处理

1. 到期前 7 天提醒；
2. 到期时立即从 Prompt 终检中排除；
3. 标记 `archived_pending_index`；
4. 触发全库双缓冲重建；
5. 索引重建失败时仍由 MySQL 终检拦截过期文档；
6. 内容负责人复核后生成新版本重新发布。

## 9. 评测脚本改造

扩展现有 `backend/scripts/evaluation/eval_recruitment.py`：

```text
--dataset
--split dev|holdout|all
--kb-snapshot
--output
--concurrency
--judge-enabled
--repeat
```

每题记录检索各阶段候选：

```text
原查询
改写查询
主题路候选
BM25 候选
向量候选
RRF 候选
重排结果
证据门禁结果
最终引用
```

这样才能定位低分来自召回、重排、证据门禁还是生成阶段。

## 11. 实施步骤

1. 固化当前知识库快照与现有评测基线；
2. 扩充并人工确认 100+ 样例；
3. 实现检索候选追踪和自动指标；
4. 实现 LLM Judge 严格 JSON 评分；
5. 增加人工抽检记录；
6. 建立 run_id 和结果文件；
7. 接入质量检查与过期规则；
8. 建立建议门禁并跑 dev；
9. 配置冻结后运行 holdout；
10. 将实测指标整理为简历可用数据。

## 12. 兜底与回滚

| 风险 | 兜底 |
| --- | --- |
| Judge 调用失败 | 保留自动指标，回答分标记待人工 |
| 单题超时 | 记录失败后继续下一题 |
| 评测中断 | 按 run_id 断点续跑 |
| 文档敏感扫描误报 | 允许人工复核，不允许自动放行 blocking |
| 过期索引尚未重建 | Prompt 前 MySQL 终检立即拦截 |
| 新配置指标退化 | 不设为默认，恢复上一版配置快照 |
| holdout 被污染 | 新建并冻结下一版本 holdout |

## 13. 验收标准

- 至少 100 条样例，类型覆盖符合计划；
- dev 与 holdout 明确分开；
- 任意两次运行可按 run_id 对比；
- 每个失败题可追溯到检索各阶段和最终引用；
- 关键权限题没有越权内容；
- 过期资料即使残留向量也无法进入 Prompt；
- 指标文件记录模型、配置、知识库快照和提交版本；
- 简历中的每个数字都能由某个结果文件重现；
- 既有后端测试通过，前端构建通过。
