## 1. 本阶段目标

把系统从“能回答”提升为“真正适合实验室招新使用”：

- 新生不知道问什么时有明确入口；
- 回答失败时给出可执行建议；
- 用户可以反馈错误、过期和引用问题；
- 管理员能把真实失败样本转化为资料修订和评测样本；
- 反馈不能未经审核直接污染知识库。

## 2. 范围边界

包含：

- 推荐问题和分类入口；
- 回答有帮助/没帮助反馈；
- 原因分类和补充意见；
- 管理端反馈分诊；
- 高频无答案、错误引用和过期资料统计；
- 脱敏后加入评测候选池。

不包含：

- 用户直接修改知识库；
- AI 根据单条反馈自动发布内容；
- 个性化推荐使用未经授权的私人长期记忆；
- 工单、邮件和企业 IM 集成。

## 3. 新生问答入口

首页推荐分类：

```text
实验室介绍
研究方向
招新对象与要求
报名与考核流程
日常学习与培养
项目与竞赛
指导教师
毕业与就业方向
```

每类展示 3～5 个推荐问题，问题来源于：

1. 管理员配置的固定问题；
2. 评测集中高价值问题；
3. 脱敏后的高频真实问题；
4. 当前资料明确可回答的问题。

不得由 LLM 临时生成尚无资料支撑的联系方式、时间和承诺。

## 4. 无答案和低置信度体验

当证据门禁拒答时，前端显示：

- 明确说明现有资料不足；
- 推荐 2～3 种可替换问法；
- 可选择相关主题；
- 展示管理员维护的正式咨询方式；
- 提供“我希望实验室补充这个问题”反馈入口。

如果只是某个子问题无证据，应回答有证据部分，并明确列出未覆盖部分，不能把整题伪装为完全回答。

## 5. 反馈数据模型

新增 `answer_feedback`：

```text
id                    feedback_ 前缀 UUID
message_id
session_id
user_id
anonymous_id
rating                helpful / unhelpful
reason_code           wrong / outdated / bad_citation / incomplete / no_answer / permission / other
comment
status                pending / triaged / resolved / ignored
reviewer_id
resolution_note
created_at
resolved_at
```

约束：

- 登录用户使用 user_id；访客使用匿名 ID；
- 一次回答每个身份只能保留一条当前反馈，可修改；
- comment 限长并做内容安全检查；
- 反馈保留当次知识库快照、模型、配置和引用 ID 的只读关联；
- 不复制完整私人长期记忆。

## 7. API 设计

问答侧：

```text
GET  /api/chat/suggested-questions
POST /api/chat/messages/{message_id}/feedback
GET  /api/chat/messages/{message_id}/feedback
DELETE /api/chat/messages/{message_id}/feedback
```

管理侧：

```text
GET  /api/admin/feedback?status=pending&reason_code=outdated
GET  /api/admin/feedback/{id}
POST /api/admin/feedback/{id}/triage
POST /api/admin/feedback/{id}/resolve
POST /api/admin/feedback/{id}/ignore
POST /api/admin/feedback/{id}/evaluation-candidate

GET    /api/admin/suggested-questions
POST   /api/admin/suggested-questions
PUT    /api/admin/suggested-questions/{id}
DELETE /api/admin/suggested-questions/{id}
```

权限：

- guest/student 可提交自己的反馈；
- 用户不能查看其他人的反馈；
- editor 可处理自己可操作知识库相关反馈；
- admin 可处理全部反馈和推荐问题。

## 8. 反馈处理闭环

```text
用户反馈
→ 自动关联问题、回答、引用、文档版本和运行配置
→ editor 分诊
→ 判断为回答问题 / 检索问题 / 资料问题 / 权限问题
→ 修订资料或配置
→ 管理员审核发布
→ 加入评测候选池
→ 下一次评测验证
→ 标记 resolved
```

反馈状态变更必须写审计。只有在新版资料已发布且对应问题通过评测后，才建议标记 resolved。

## 9. 管理端看板

展示：

- 待处理和超时反馈；
- helpful 比例；
- 按 reason_code 分布；
- 高频无答案问题；
- 被投诉最多的文档和引用；
- 疑似过期资料；
- 最近 7/30 天趋势；
- 已转入评测候选但未确认的样本。

数据较少时只显示数量和列表，不绘制没有意义的复杂图表。

## 10. 隐私和防滥用

- feedback comment 做长度、频率和内容限制；
- 访客按匿名 ID 和 IP 哈希限流；
- 导入评测集前删除姓名、手机号、学号等个人信息；
- 管理端默认不展示访客 IP；
- 用户删除会话时，反馈是否保留按隐私策略执行，但至少解除可识别关联；
- 反馈不得影响当前回答或自动改变用户权限。

## 13. 兜底与回滚

| 风险 | 兜底 |
| --- | --- |
| 推荐问题接口失败 | 问答输入框继续可用，不阻断自由提问 |
| 反馈写入失败 | 提示稍后重试，不影响已生成回答 |
| 恶意批量反馈 | 限流、匿名 ID 和重复约束 |
| 反馈含敏感信息 | 脱敏并标记人工检查，不进入评测集 |
| 反馈误判 | 管理员可改分诊结果，保留历史审计 |
| 高频问题没有资料 | 进入资料补充队列，不让 LLM 编造 |
| 管理看板聚合失败 | 退化为分页反馈列表 |

## 14. 验收标准

- 访客首次进入即可看到分类推荐问题；
- 推荐接口失败不影响自由提问；
- 用户可以评价自己的回答，不能查看他人反馈；
- 反馈可追溯到当次问题、回答、引用和知识库快照；
- 反馈不会自动修改或发布知识库；
- editor/admin 权限符合资源范围；
- 高频无答案问题可脱敏进入评测候选池；
- 修订发布并通过评测后可关闭反馈；
- 既有后端测试通过，前端构建通过。
