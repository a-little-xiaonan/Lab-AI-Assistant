## 1. 本阶段目标

把当前 FastAPI `BackgroundTasks` 和进程内任务状态改造成可恢复、可重试、可观察的后台任务系统，解决：

- API 进程重启后任务丢失；
- 多 worker 无法共享任务状态和互斥锁；
- 文档发布、重索引和评测耗时较长；
- 管理员看不到任务进度、失败原因和重试记录。

技术选型：Redis + RQ + MySQL 任务表。

## 2. 为什么选择 RQ

当前任务主体都是同步 Python 函数，RQ 的迁移成本比 Celery 低：

- 不需要改造成异步协程；
- Redis 同时承担队列、分布式锁和短时状态；
- 部署结构简单，适合单机或小规模实验室服务器；
- MySQL 继续作为用户可见任务状态的事实源。

保留两种模式：

```text
TASK_MODE=inline   本地开发，当前进程直接执行
TASK_MODE=rq       联调和部署，交给独立 Worker
```

两种模式必须调用同一业务任务函数，避免产生两套逻辑。

## 5. 任务服务设计

新增统一入口：

```python
enqueue_job(job_type, resource, requested_by, payload) -> BackgroundJob
run_job(job_id)
update_progress(job_id, current, total, detail=None)
heartbeat(job_id)
retry_job(job_id, actor)
cancel_job(job_id, actor)
```

业务任务签名统一：

```python
def execute_<job_type>(context: JobContext, payload: dict) -> dict:
    ...
```

`JobContext` 提供进度、心跳、取消检查和结构化日志，不让业务函数直接依赖 RQ API。

## 6. 幂等与互斥

### 6.1 幂等键

示例：

```text
document_prepare:{document_id}:{version_no}
kb_publish:{kb_id}:{publish_revision}
kb_reindex:{kb_id}:{index_revision}
evaluation:{dataset_version}:{kb_snapshot}:{config_hash}
```

相同幂等键已有 queued/running/succeeded 任务时不重复创建；失败任务只有显式 retry 才增加 attempt。

### 6.2 分布式锁

```text
lock:document:{doc_id}:prepare
lock:kb:{kb_id}:publish
lock:kb:{kb_id}:reindex
```

知识库 publish 与 reindex 互斥。锁设置 TTL，Worker 持续续租；业务执行前同时检查 MySQL 任务状态，避免 Redis 锁过期导致双执行。

### 6.3 数据一致性

- 向量 ID 使用稳定的文档版本号和 chunk_index；
- 写正式状态前检查任务仍未取消；
- 发布双 buffer 的 swap 只允许一个任务执行；
- 任务重试不得新增重复 Chunk、审核记录或文档版本；
- result_json 只保存小型摘要，大结果写文件并保存路径。

## 7. 重试策略

可重试：

- DashScope 429、5xx；
- 网络超时；
- Redis 短暂断连；
- ChromaDB 临时锁冲突。

不可自动重试：

- 权限不足；
- 文件损坏；
- 敏感扫描 blocking；
- 状态机非法；
- 数据一致性校验失败。

默认最多 3 次，指数退避。最终失败保留错误码、用户可读信息和 request_id，由管理员决定是否重试。

## 8. 服务重启恢复

启动恢复任务：

1. 查询 `status=running` 且 heartbeat 超时的任务；
2. 若幂等任务允许恢复，重置为 queued 并重新入队；
3. 不可安全恢复的任务标记 failed；
4. 检查遗留 `docs_new/docs_old` collection；
5. 根据数据库发布 revision 判断恢复、清理或回滚；
6. 记录恢复审计。

API 进程不主动执行重任务，只负责创建任务。Worker 数量第一版设为 1，确认幂等和锁正确后再扩展。

## 9. API 设计

```text
GET  /api/system/jobs?status=running&job_type=kb_publish
GET  /api/system/jobs/{job_id}
POST /api/system/jobs/{job_id}/retry
POST /api/system/jobs/{job_id}/cancel
```

权限：

- editor 只能看自己发起或自己可操作知识库的任务；
- admin 可看全部任务、重试和取消；
- student/guest 无权访问；
- 已进入不可中断 swap 阶段的任务拒绝取消。

## 10. 前端设计

系统管理后台新增任务中心：

- queued/running/succeeded/failed 数量；
- 类型、资源、发起人、进度、耗时和 attempt；
- 失败原因和 request_id；
- 管理员重试和取消；
- 知识库工作台显示当前文档处理/发布任务；
- 优先 SSE 推送进度，断线后退化为 2 秒轮询；
- 页面卸载时停止轮询。

## 14. 兜底与回滚

| 风险 | 兜底 |
| --- | --- |
| Redis 不可用 | 问答继续；需要异步的写操作返回可重试 503 |
| Worker 重启 | MySQL 心跳扫描后重新入队或标记失败 |
| 重复投递 | 幂等键和资源锁阻止重复执行 |
| 锁意外过期 | MySQL 任务状态和 revision 二次校验 |
| 任务最终失败 | 保留旧索引、错误码和手动重试入口 |
| SSE 断线 | 前端退化轮询 |
| RQ 方案需回退 | TASK_MODE 改回 inline，业务函数不变 |

## 15. 验收标准

- API 重启不丢已入队任务；
- Worker 重启后任务可恢复或明确失败；
- 同一知识库不会并发 publish/reindex；
- 重试不产生重复 Chunk、版本和审核记录；
- Redis 故障不影响只读问答；
- editor 看不到无权知识库任务；
- admin 可查看、重试和取消允许取消的任务；
- inline 与 rq 模式产出一致；
- 既有后端测试通过，前端构建通过。
