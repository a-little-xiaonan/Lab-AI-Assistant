## 1. 使用方式

原有单篇总方案已拆成七个可独立执行的任务包。后续执行时，直接指定文档编号，例如：

```text
按照 01-M0-数据库迁移与权限收口.md 开始实施。
```

每个任务包都包含：

- 当前基础与目标；
- 明确的范围和非范围；
- 数据模型与接口；
- 后端、前端文件清单；
- 分步实施顺序；
- 失败兜底与回滚方式；
- 验收标准和完成记录。

执行约定：

1. 一次只实施一份任务包；
2. 当前任务验收通过后再进入下一份；
3. 不把设计文档提交到 GitHub；
4. 不在代码、日志、提交信息或文档中写入 API Key、JWT 密钥、数据库密码和管理员密码；
5. 遵循当前约定，不新增测试用例，但必须运行既有测试、前端构建和对应的人工验收；
6. 代码注释、日志和 Git 提交信息使用中文；
7. 不顺手修改当前任务包之外的功能。

## 2. 系统目标

系统最终分为三个产品区域：

1. **智能问答区**：访客、普通学生、实验室成员和管理员均可访问；后端按身份自动选择可读知识库。
2. **知识库工作台**：仅实验室成员和管理员访问；完成资料上传、AI 初标、人工审核、版本和索引管理。
3. **系统管理后台**：实验室成员可查看授权范围内的运行概览；管理员负责用户、角色、成员申请、审计和失败任务。

可信内容供应链：

```text
资料上传到隔离区
→ 解析与自动质量检查
→ AI 主题初标和风险提示
→ 实验室成员预审
→ 管理员批准发布
→ 双缓冲构建正式索引
→ 授权检索和证据门禁
→ 带引用回答
→ 用户反馈与离线评测
```

默认按编号顺序执行最稳妥。若额度有限，优先完成：

```text

```

这三步先解决权限一致性、未经审核资料泄漏和效果无法量化三个核心问题。

## 5. 全局关键决策

### 5.1 权限只有一个事实源

第一版使用知识库 `access_level`：

```text
guest < student < editor < admin
```

读取时允许高级角色向下读取；管理操作按资源与 action 统一判断。旧 ACL 表和接口不得继续成为不生效的孤岛配置。

### 5.2 技术状态与内容状态分离

- `documents.status`：`processing / ready / failed / reindexing`，表示技术处理结果；
- `documents.governance_status`：`draft / pending_review / publishing / published / rejected / archived / deleted`，表示内容是否允许对用户生效。

只有技术处理成功且内容已发布的文档才能进入 Prompt。

### 5.3 AI 不直接发布内容

AI 只输出主题、摘要、关键词、访问级别和风险建议。最终发布、降低权限、删除版本必须由有权限的人工完成。

### 5.4 发布优先保证正确性

当前只有几十份实验室资料，发布、归档和回滚统一采用全库双缓冲重建。新索引完整校验成功后再切换，失败时继续使用旧索引。

### 5.5 简历数据必须可复现

准确率、召回率、延迟、Token 和成本只能填写实际评测结果，并能追溯到评测集版本、知识库快照、模型和配置。

## 6. 暂不实施

以下功能继续后置，避免毕设范围失控：

- 树形意图分类器、MCP 调度和 SYSTEM 指令路由；
- 多组织、多租户；
- 字段级 ABAC；
- 数千份资料之前的差量向量发布；
- AI 自动修改或直接发布知识库；
- 微服务、Kubernetes 和复杂消息中间件。
