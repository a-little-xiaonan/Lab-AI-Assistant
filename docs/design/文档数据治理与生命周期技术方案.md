# 文档数据治理与生命周期技术方案

> **文档状态**：待实施设计
> **适用范围**：实验室招新资料、培训资料、项目材料及后续新增知识文档
> **核心目标**：确保进入知识库的内容可用、可信、不过期、不过权，并且每次修改都可追踪和回滚。

## 1. 为什么需要单独的数据治理层

当前系统已经能解析、分块、向量化和检索文档，但“成功入库”只说明技术链路成功，不代表内容适合直接回答新生。实验室历史资料常见以下问题：

- 同一材料存在多个年份、多个版本，内容互相冲突；
- 压缩包、安装包、源码依赖、日志和临时文件混入资料目录；
- 电话、账号、名单、密钥等敏感信息不适合公开检索；
- 旧招新时间、旧负责人和旧比赛数据已经失效；
- 扫描件、乱码文件、表格空行等导致文本质量差；
- AI 主题标注可能错误，不能未经审核就影响定向检索。

因此需要把“技术处理状态”和“内容治理状态”分开：

```text
上传文件
  ├─ 技术处理：解析 → 分块 → 向量化 → ready / failed
  └─ 内容治理：草稿 → 自动检查 → 人工审核 → 发布 / 驳回 / 归档
```

只有同时满足 `processing_status=ready` 与 `governance_status=published` 的文档，才能进入用户检索链路。

## 2. 总体架构

```text
隔离区上传
   ↓
文件安全与格式检查
   ↓
哈希去重 + 近重复识别 + 版本判断
   ↓
文本解析与质量检测
   ↓
敏感信息扫描 + 知识库级别建议 + 主题初标
   ↓
管理员审核
   ├─ 驳回：记录原因，不进入检索
   ├─ 退回修改：生成新版本后重新审核
   └─ 发布：分块、向量化、关键词索引原子切换
                     ↓
            到期复核 / 归档 / 删除
```

设计原则：

1. **默认不发布**：新资料先进入隔离区，自动检查不能替代人工审核。
2. **原文件不覆盖**：修改产生新版本，旧版本可回滚。
3. **权限在索引前生效**：文档级别不得高于知识库授权边界；未授权内容不能先进入模型再隐藏。
4. **发布原子化**：新索引构建成功后再替换旧索引，失败继续使用旧版本。
5. **删除可恢复**：业务删除先逻辑删除，达到保留期后再物理清理。

## 3. 文档状态模型

### 3.1 两套状态分别负责什么

技术处理状态沿用现有 `documents.status`：

| 状态 | 含义 |
| --- | --- |
| `processing` | 正在解析、分块或向量化 |
| `ready` | 技术处理成功，但不代表已经公开 |
| `failed` | 格式、解析、Embedding 或索引失败 |

新增治理状态 `governance_status`：

| 状态 | 含义 | 是否可检索 |
| --- | --- | --- |
| `draft` | 刚上传或编辑中的草稿 | 否 |
| `pending_review` | 自动检查完成，等待人工审核 | 否 |
| `published` | 已审核并发布 | 是 |
| `rejected` | 审核驳回 | 否 |
| `archived` | 历史版本或已过期内容 | 否 |
| `deleted` | 逻辑删除，等待清理 | 否 |

### 3.2 状态流转

```text
draft → pending_review → published
  │           │              │
  │           └→ rejected    ├→ archived
  └→ deleted                 └→ 新版本 pending_review
```

禁止从 `draft` 直接发布。管理员可以驳回 AI 建议，但发布动作必须记录审核人、时间和备注。

## 4. 数据模型

### 4.1 documents 表扩展

```text
documents
- governance_status       draft / pending_review / published / rejected / archived / deleted
- sensitivity_level       public / student / editor / admin
- current_version         当前发布版本号
- owner_id                内容负责人
- effective_at            生效时间
- expires_at              到期复核时间
- reviewed_by             最后审核人
- reviewed_at             最后审核时间
- deleted_at              逻辑删除时间
```

`sensitivity_level` 必须不低于知识库的访问级别；若自动扫描发现更敏感内容，只允许提高级别，不能自动降低。

### 4.2 document_versions 文档版本表

```text
document_versions
- id
- document_id
- version_no
- file_path
- file_hash
- file_size
- content_hash            归一化文本哈希
- change_summary
- created_by
- created_at
- processing_status
- chunk_count
- index_snapshot          对应索引版本标识
```

同一个 `document_id` 表示同一份业务资料，`document_versions` 保存每次上传或编辑后的不可变快照。

### 4.3 document_quality_checks 自动检查结果

```text
document_quality_checks
- id
- document_version_id
- check_type              duplicate / sensitive / encoding / empty / stale / conflicting
- severity                info / warning / blocking
- result                  passed / failed / needs_review
- details_json
- created_at
```

### 4.4 document_reviews 人工审核记录

```text
document_reviews
- id
- document_version_id
- reviewer_id
- action                  approve / reject / request_change / archive
- comment
- created_at
```

审核记录不可覆盖，只能追加，便于追溯“谁在什么时间依据什么理由发布了哪一版”。

## 5. 自动治理规则

### 5.1 文件级安全检查

- 以 MIME 和文件头为准校验格式，不只信任扩展名；
- 文件大小继续限制 50 MB；压缩包额外限制解压总大小、文件数和压缩层级，防止压缩炸弹；
- 拒绝可执行文件、脚本安装包、宏和损坏文件；
- 文件名清理路径字符，原文件保存到以 UUID 命名的隔离目录；
- 文件扫描失败时不得进入发布流程。

### 5.2 去重与版本识别

分三层判断：

1. `file_hash` 完全相同：同一知识库内直接提示重复，不重复解析；
2. `content_hash` 相同：版式不同但正文一致，提示复用已有文档；
3. SimHash/MinHash 近重复：相似度超过阈值时标记 `needs_review`，由管理员选择“新版本”或“独立文档”。

不同年份的招新资料不能因相似而自动删除，应保留版本并明确生效时间。

### 5.3 文本质量检查

- 有效正文长度、空页比例、乱码比例、重复段落比例；
- PDF 是否只有扫描图；无文本层时提示需要 OCR，而不是产生空 Chunk；
- Excel 是否存在连续空行、公式错误或仅样式无数据；
- 标题层级和段落是否异常；
- Chunk 过短、过长、重复率异常时阻止发布并给出定位信息。

### 5.4 敏感信息检查

自动识别并定位：

- 手机号、身份证号、邮箱、学号、个人名单；
- API Key、密码、数据库连接串、Access Token；
- 内网地址、私有系统账号、未公开联系方式；
- 标记为内部、保密、禁止外传的段落。

处理方式按风险分级：

- 明确密钥和密码：阻断发布；
- 手机号、名单等个人信息：默认阻断公开发布，允许管理员脱敏后生成新版本；
- 可能敏感：提升到 `editor/admin` 级别并要求二次审核；
- 检测失败：保持隔离，不以“未发现风险”处理。

### 5.5 AI 初标与人工复核

AI 可以给出：

- 文档摘要；
- 主题标签建议；
- 访问级别建议；
- 时效性字段建议；
- 与已有文档可能冲突的段落。

AI 输出统一标为 `suggested`，不得直接修改发布级别或检索范围。管理员审核后写入 `approved` 记录，才同步到 Chunk 元数据和检索索引。

## 6. 发布、更新与回滚

### 6.1 发布流程

```text
审核通过
  → 为待发布版本生成完整 Chunk
  → 写入临时 Chroma collection 和临时关键词索引
  → 校验 Chunk 数、文档 ID、Embedding 维度
  → 原子切换为当前索引
  → 更新 current_version 与 published 状态
```

复用项目现有双 Buffer 重索引能力。索引构建失败时，数据库保持旧版本为 `published`，新版本标记失败，线上检索不中断。

### 6.2 冲突内容处理

当新版本与当前版本在时间、人数、负责人、报名要求等关键事实上冲突时：

- 不允许两版同时参与检索；
- 管理页面并排展示冲突片段；
- 管理员选择新版本生效时间并归档旧版本；
- 回答时优先选择当前有效版本，过期资料只能由管理员查看。

### 6.3 回滚

回滚不是重新上传旧文件，而是把历史 `document_version` 复制成一个新的发布版本，并重新走审核与索引切换，保证审计时间线连续。

## 7. 权限规则

| 操作 | guest | student | editor | admin |
| --- | ---: | ---: | ---: | ---: |
| 检索已授权且已发布资料 | ✓ | ✓ | ✓ | ✓ |
| 查看草稿与审核结果 |  |  | ✓（授权库） | ✓ |
| 上传草稿 |  |  | ✓（授权库） | ✓ |
| 提交审核 |  |  | ✓（授权库） | ✓ |
| 最终发布、回滚、修改访问级别 |  |  |  | ✓ |
| 查看敏感命中原文与审计日志 |  |  | 受限 | ✓ |

所有下载、预览、Chunk 查看、重索引和检索接口都复用同一权限服务，不能只在前端隐藏按钮。

## 8. API 与管理界面

建议新增接口：

```text
POST /api/knowledge-bases/{kb_id}/documents/drafts
GET  /api/documents/{doc_id}/versions
GET  /api/documents/{doc_id}/quality-checks
POST /api/documents/{doc_id}/submit-review
POST /api/document-versions/{version_id}/approve
POST /api/document-versions/{version_id}/reject
POST /api/document-versions/{version_id}/publish
POST /api/documents/{doc_id}/rollback/{version_no}
POST /api/documents/{doc_id}/archive
```

管理界面需要展示：技术状态、治理状态、敏感级别、当前版本、检查项、AI 建议、审核记录和到期时间。阻断项必须在发布按钮附近明确显示，不能藏在日志里。

## 9. 每一步的兜底策略

| 环节 | 正常路径 | 失败时兜底 |
| --- | --- | --- |
| 格式识别 | 文件头 + 专用解析器 | 转 Unstructured；仍失败则标记 failed，不猜格式 |
| 去重 | 哈希 + 近重复识别 | 近重复模型失败时只做精确哈希，不自动删除 |
| 文本质量 | 自动规则评分 | 检查器异常时进入人工审核，不默认通过 |
| 敏感扫描 | 规则 + 可选模型识别 | 扫描异常时保持隔离，禁止公开发布 |
| AI 主题/级别建议 | 输出待审核建议 | 调用失败不影响上传，管理员手工填写 |
| 人工审核 | 管理员确认发布 | 审核记录写入失败时不执行索引切换 |
| 索引构建 | 临时索引完成后原子交换 | 失败保留旧索引，新版本标失败并可重试 |
| 到期复核 | 到期前通知负责人 | 未及时复核时自动停止公开检索，不物理删除 |
| 删除 | 逻辑删除 + 保留期 | 清理任务失败可重试，期间始终不可检索 |

## 10. 实施顺序

1. 为 `documents` 增加治理状态、敏感级别和版本字段，创建版本/检查/审核三张表；
2. 上传改为隔离区草稿，不再处理完成即默认发布；
3. 实现精确去重、基础质量检查和敏感信息规则扫描；
4. 增加管理员审核页，接入现有 AI 主题初标；
5. 把发布动作接到双 Buffer 索引切换，并在检索层强制过滤 `published`；
6. 增加到期复核、归档、逻辑删除和审计日志；
7. 最后加入近重复检测、冲突段落提示与 OCR 等增强能力。

## 11. 验收指标

- 未审核、驳回、归档和逻辑删除文档的检索泄露率必须为 0；
- 明文密钥、密码和身份证号样例的公开发布阻断率必须为 100%；
- 完全重复文件识别率 100%，且不产生重复 Chunk；
- 发布失败时旧索引可用率 100%；
- 任意已发布回答能够定位到文档版本、审核人和生效时间；
- 到期资料停止参与普通检索，管理员仍能查看和恢复；
- 所有发布、回滚、权限变更和物理删除操作都有不可覆盖的审计记录。
