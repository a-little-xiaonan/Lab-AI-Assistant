# 复杂问题拆解与意图定向检索实现方案

> **状态**：核心代码已实现，默认关闭，待按主题标注文档后灰度启用
> **关联简历点**：查询理解层（复杂问题拆解）与双路召回（意图定向检索 + 全局向量检索）
> **前置能力**：现有 Query Rewrite、BM25 + 向量 RRF 融合、Re-ranking、知识库 ACL 与文档 Chunk 元数据

## 1. 要解决什么

当前系统已能把一个问题改写为多种检索表达，并通过 BM25 与向量召回回答。例如“实验室怎么招新？”能找到语义接近的资料。

但下面两类问题仍有缺口：

1. **复杂组合问题**：如“实验室主要做什么、招新要求是什么、加入后可以参与哪些项目？”包含三个可独立检索的事实点。只做 Query Rewrite 容易把它仍当成一个长句检索，导致某一部分漏召回。
2. **有明确主题边界的问题**：如“招新时间、报名方式是什么？”应该优先检索“招新”资料，而不是与“项目展示”“技术栈”同等竞争；但又不能完全放弃全局检索，以免资料标签错漏。

本方案新增两层能力：

```text
原问题
  ├─ 查询规划：判断单问题 / 多子问题，必要时拆分
  ├─ 意图定向召回：按资料主题过滤的局部检索
  └─ 全局混合召回：现有 BM25 + 向量检索
            ↓
     两路 / 多子问题结果融合 → 重排序 → 一次性生成带引用答案
```

这里的“意图”只表示**知识主题**，例如招新、实验室介绍、项目成果、技术学习、活动管理；它不等同于之后再实现的“知识库 / MCP / SYSTEM”树形意图路由。

## 2. 设计原则

- **先判断是否值得拆**：普通问题保持现有路径，避免每次都多一次 LLM 调用和多轮检索。
- **拆问题，不拆最终回答**：子问题并行检索；最终仍由一次回答模型统筹生成，避免多段回答风格不一致和 Token 成本翻倍。
- **局部召回是加分项，不是唯一来源**：每个子问题都同时保留主题定向和全局检索，避免标签错误造成漏召回。
- **知识库 ACL 永远先执行**：只能在当前用户可读的 `kb_id` 中检索，意图过滤不能绕开知识库授权。
- **所有决策可降级**：规划器、标签、局部查询任一失败时回退现有 `hybrid_retriever.retrieve()`，主聊天链路不受影响。

## 3. 数据建模：为文档和 Chunk 增加可检索主题

### 3.1 主题词表

先用受控配置而不是自由文本标签。建议文件：`data/retrieval_topics.json`。

```json
{
  "topics": [
    {"code": "lab_intro", "name": "实验室介绍", "aliases": ["实验室做什么", "研究方向", "工作室简介"]},
    {"code": "recruitment", "name": "招新", "aliases": ["报名", "面试", "招人", "纳新", "加入实验室"]},
    {"code": "projects", "name": "项目成果", "aliases": ["项目", "比赛", "成果", "作品"]},
    {"code": "learning", "name": "技术学习", "aliases": ["学习路线", "技术栈", "培训", "培养"]},
    {"code": "activities", "name": "活动与管理", "aliases": ["活动", "社团", "值班", "管理"]}
  ]
}
```

配置使用 mtime 热加载，和现有术语映射表一致；新增主题不需重启服务。

### 3.2 文档主题与 Chunk 元数据

新增表 `document_topics`，一篇文档可有多个主题：

```text
document_topics
- document_id        FK documents.id
- topic_code         retrieval_topics.code
- source             manual / filename_rule / llm_suggested
- confidence         nullable
- created_at
- UNIQUE(document_id, topic_code)
```

向量入库时，把文档主题复制到 Chroma Chunk metadata：

```json
{
  "doc_id": "doc_xxx",
  "topic_codes": ["recruitment", "lab_intro"]
}
```

Chroma 对数组 where 条件的版本兼容性需要先验证。因此首期推荐：主题过滤由 MySQL 的 `document_topics` 先找出允许的 `doc_id`，再在应用层筛选向量/BM25 候选；规模扩大后再评估 Chroma metadata filter 或按主题建索引。

### 3.3 主题标注方式

按可靠度从高到低：

1. 管理员上传或管理页面手动勾选主题；这是权威来源。
2. 文件名、目录名规则建议主题，例如名称含“招新”“纳新”建议 `recruitment`。
3. LLM 仅作为建议，不直接覆盖人工标签；管理端显示“待确认”。

未标主题的历史文档仍参与全局检索，不会消失。

## 4. 查询规划：单问题与多子问题

新增模块：`backend/app/core/retrieval/planning/query_planner.py`。

### 4.1 内部契约

```python
@dataclass
class QueryPlan:
    original_query: str
    mode: Literal["single", "multi"]
    sub_queries: list[str]              # single 时恒为 [original_query]
    topic_hints: list[list[str]]        # 与 sub_queries 对齐，例如 [["lab_intro"], ["recruitment"]]
    answer_order: list[int]             # 输出时子问题组织顺序

def plan_query(query: str, history_context: str = "") -> QueryPlan:
    ...
```

约束：最多 **3** 个子问题，每条最多 120 字，总长度受限；原问题始终保留。

### 4.2 两级判断，控制成本

第一层是规则快速判定；命中以下信号才调 LLM：

- 有明显并列连接词：`以及 / 和 / 还想知道 / 分别 / 同时`；
- 有多个问号或枚举编号；
- 主题词命中两个及以上，例如“招新”和“项目”；
- 当前对话历史表明用户在追问多个不同主题。

未命中则直接返回单问题，不新增 LLM 成本。

第二层由 LLM 输出严格 JSON：

```json
{
  "needs_decomposition": true,
  "sub_queries": [
    {"question": "实验室主要研究或开发哪些方向？", "topics": ["lab_intro"]},
    {"question": "本次招新的报名方式和要求是什么？", "topics": ["recruitment"]},
    {"question": "新成员可以参与哪些项目？", "topics": ["projects"]}
  ]
}
```

解析失败、子问题重复、数量超限、出现与原问题无关内容时，直接降级为单问题。不要让规划器抛异常到聊天接口。

### 4.3 与现有 Query Rewrite 的分工

| 能力 | 解决的问题 | 输出 |
| --- | --- | --- |
| Query Planner | 一个问题里有几件事 | 1～3 个子问题 + 主题提示 |
| Query Rewrite | 同一件事的不同说法 | 每个子问题的 1～3 条同义检索表达 |
| 术语映射 | 口语名和标准名不一致 | 关键词侧的确定性扩展 |

执行顺序：**先拆分，后改写**。最多 3 个子问题 × 每题最多 3 条改写，必须设置总查询上限 `MAX_RETRIEVAL_QUERIES=6`；超过时优先保留所有子问题的原句，再保留改写。

## 5. 意图定向检索 + 全局检索

新增模块：`backend/app/core/retrieval/topic_retriever.py`，由新编排器调用。

### 5.1 每个子问题的两路召回

```text
子问题 q + topic_hints
    ├─ 定向路：在 topic 对应文档集合中执行 BM25 + 向量 RRF
    └─ 全局路：调用现有 hybrid_retriever（BM25 + 向量 RRF）
                 ↓
        子问题级 RRF 融合（定向 1 份 + 全局 1 份）
```

定向路和全局路并行。每路取 `top_k=10`，子问题级融合保留 12 条候选。即使主题为空或没有命中，全局路仍正常工作。

不要简单给定向路固定 0.7 权重，因为 BM25、余弦、RRF 的分数不可直接比较；使用第二层 RRF 更稳：

```text
score(chunk) = 1 / (60 + rank_in_topic) + 1 / (60 + rank_in_global)
```

### 5.2 跨子问题融合与覆盖保护

三个子问题各自排名后，如果直接拼接，很容易让第一个主题占满上下文。增加“覆盖保护”：

1. 每个子问题先保留前 3 个候选；
2. 再按融合分补齐总候选集到 20；
3. 使用现有 Reranker 对“原问题 + 子问题列表”重排序；
4. 重排序后仍确保每个子问题至少有一个候选，否则从该子问题候选中回填；
5. 最后沿用现有 `max_context_tokens=3000` 截断。

这样不会因为“招新”资料分数高，就把“项目”问题完全挤出上下文。

### 5.3 检索编排伪代码

```python
def retrieve_with_plan(kb_id: str, query: str, history: str) -> list[RetrievedChunk]:
    plan = plan_query(query, history)

    sub_results = parallel_map(
        lambda sub, topics: retrieve_one_sub_question(kb_id, sub, topics),
        zip(plan.sub_queries, plan.topic_hints),
        max_workers=3,
    )
    candidates = merge_with_coverage(sub_results, limit=20)
    reranked = rerank(query, candidates) if settings.rerank_enabled else candidates
    return ensure_coverage_then_trim(reranked, sub_results, settings.max_context_tokens)
```

现有 `hybrid_retriever.retrieve()` 保留不改，作为全局路和全部降级路径。新入口建议命名为 `retrieval_orchestrator.retrieve()`，`rag_pipeline._prepare()` 只调用这一个入口，避免业务判断散落到 Pipeline 中。

## 6. Prompt 与答案组织

检索得到的 Chunk 必须附带 `sub_question_indexes`，提示模型哪些资料服务于哪个子问题。

```text
用户原问题：实验室主要做什么、招新要求是什么、加入后能参与哪些项目？

请按以下顺序回答；每一项只使用分配给它或公共的参考资料：
1. 实验室方向
2. 招新要求
3. 可参与项目

资料不足时明确写“知识库未找到相关资料”，不要根据常识补充。
```

最终只调用一次回答模型。回答建议使用编号小节，并沿用 `[来源: 文件名 P页码]` 与“参考来源”汇总协议。

如果规划器判断为单问题，继续使用当前 Prompt 和回答格式，不产生额外标题或结构。

## 8. 实施顺序

1. **主题基础**：创建主题配置、`document_topics` 表、管理端文档主题勾选；历史文档先人工标注高价值招新资料。
2. **定向检索**：实现主题文档筛选与“定向 + 全局”二层 RRF，但先以单问题接入；用已有 QA 样例做开关对比。
3. **查询规划**：实现规则触发、LLM JSON 规划器和严格降级；只输出计划日志，不改变检索，观察一轮。
4. **复杂问题并行检索**：接入多子问题、覆盖保护、Prompt 结构化回答。
5. **评估与灰度**：新增至少 20 条复杂问题样例；只有引用正确率不下降、复杂题覆盖率提升后才默认开启。

## 9. 验收标准

- “实验室做什么、怎么报名、能做什么项目？”能拆成 3 个不重复子问题，并给每一部分至少一条可追溯引用或明确的资料不足提示。
- “实验室招新时间是什么？”保持单问题路径，不调用规划 LLM。
- `recruitment` 主题定向资料与全局资料都参与候选；删除主题标签后，全局检索仍可回答。
- 规划 LLM、主题配置、局部检索任一失败时，系统退回当前混合检索链路且正常回答。
- 普通问题的 P95 延迟不因关闭开关而发生变化；开启复杂规划后的额外成本与延迟有日志可观测。
- 所有路径继续先校验知识库 `read` 权限，不能通过 topic 参数读取无权知识库。

## 10. 逐层兜底与降级策略

原则：每一层只能增强召回或组织效果，**不能成为聊天链路的单点故障**。任何增强失败时向下退一级，最终回到当前已稳定的“原问题 → 混合检索 → 重排 → RAG 回答”路径。

| 环节 | 正常路径 | 失败、空结果或不可信结果时的兜底 |
| --- | --- | --- |
| 主题配置 | 读取 `retrieval_topics.json`，按 mtime 热加载 | 配置不存在、JSON 非法或热加载失败：禁用主题提示，仅保留全局检索 |
| 文档主题标注 | 人工标注优先，文件名规则、LLM 仅给建议 | 文档无主题、主题错漏：文档仍保留在全局索引中，不影响全局召回 |
| 是否拆分判断 | 规则命中后调用 LLM 输出 JSON 计划 | LLM 超时、JSON 解析失败、子问题偏题：按单问题处理 |
| 子问题生成 | 最多 3 个、去重且与原问题相关 | 数量超限、重复、空文本：丢弃整个拆分结果，改用原问题 |
| Query Rewrite | 对每个有效子问题生成同义检索表达 | 改写失败：保留该子问题原句；原始问题永远保留 |
| 定向检索 | 在主题文档集合内跑 BM25 + 向量召回 | 主题为空、主题无命中、局部索引异常：该路返回空，由全局路继续承担召回 |
| 全局混合检索 | 现有向量 + BM25 + RRF | 一侧失败时使用另一侧；两侧均失败时进入“未找到资料”分支，不编造 |
| 子问题结果融合 | 定向路与全局路再做 RRF 融合 | 融合计算异常：直接采用同一子问题的全局混合检索结果 |
| Re-ranking | 对融合后的候选精排 | 重排 API、模型或解析失败：保留 RRF 原始顺序 |
| 覆盖保护 | 每个子问题至少保留 1 条候选资料 | 某子问题没有任何资料：在 Prompt 中显式标记该部分“知识库未找到相关资料” |
| Prompt 上下文控制 | 每题候选 + 公共候选一起进入上下文 | Token 超限时先压缩每题候选，再保留每题最高分资料；仍超限按子问题顺序截断并记录日志 |
| 最终生成 | 一次性按子问题组织回答并附引用 | LLM 失败返回统一可读错误；禁止以缓存的旧回答或模型常识替代资料答案 |

完整降级链如下：

```text
主题/规划/局部检索任一失败
        ↓
单问题 + 原始查询
        ↓
现有 Query Rewrite（失败则只保留原查询）
        ↓
现有 BM25 + 向量 RRF 混合检索
        ↓
现有 Re-ranking（失败则保留 RRF 顺序）
        ↓
现有 RAG Prompt 与引用回答
```

因此，即使两个新开关全部关闭、主题配置损坏，或规划服务不可用，系统也必须保持当前版本的问答能力和权限校验语义。

## 11. 与“树形意图分类器”的边界

本方案只处理“资料主题定向检索”，不会调用 MCP，也不会执行系统指令。以后实现树形意图分类器时，可把这里的 `topic_hints` 作为其“知识库分支”的下游输入：

```text
树形路由：knowledge_base / MCP / SYSTEM
                  │
                  └─ knowledge_base → 查询规划 → 主题定向 + 全局检索
```

因此现在不必等待 Redis、MCP 或澄清交互，就可以先完成第 3、4 点中与 RAG 检索直接相关的能力。
